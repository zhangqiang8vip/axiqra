维护方式：本文件是新文档体系入口，后续每新增、重写、废弃或归档一份核心文档，都必须同步更新本文档。

## 1. 文档定位

本文档是 Axiqra 重构后文档体系的总入口。

自 2026-06-02 起，项目正式产品名采用 `Axiqra`。旧文档、历史资料、源码目录或文件名中出现的 `DevMemory` 均视为历史名称；后续新文档、页面文案、接入说明和对外传播统一使用 `Axiqra`。旧资料来源路径保留原文件名，不因改名而改写为不存在的路径。

它不承担产品介绍、需求说明、技术方案、页面说明、治理制度或商业方案正文。它只负责四件事：

1. 说明新文档体系由哪些文件组成。
2. 说明每个新文档继承哪些旧资料中的有效内容。
3. 说明旧资料如何被归并、废弃、归档和替代。
4. 说明后续文档维护、确认、变更和追踪规则。

旧资料后续可以归档或作废，但其中的有效内容不能丢失。新文档的目标不是引用旧文档，而是把旧资料中已经存在的产品结构、技术结构、治理结构、接入结构、数据结构、页面结构和运行制度，重新消化后写成一套可以长期维护的新文档体系。

本文档不直接复制旧文档原文。后续正式文档也不直接引用旧文档正文。旧文档只作为内容依据、历史证据和重构来源。

## 4. 冲突处理规则

旧资料之间存在大量重复、覆盖和阶段性冲突。后续写作按以下规则处理。

| 冲突类型 | 处理规则 | 示例处理 |
|---|---|---|
| 同主题多份文档重复 | 后出专题文档优先，早期大文档补充背景和细节 | 产品定位以当前愿景和后执行文档为主，旧宣传册只保留有效机制 |
| 技术路线前后冲突 | 后出的规模化纠偏文档优先 | 技术架构和搜索架构以全量技术架构、百亿级搜索专项为准 |
| 页面文档与源码不一致 | 原型源码的布局、配色、路由和 mock 对象优先 | D03 以 Vue 原型为视觉基准 |
| MVP 范围过窄 | 采用“完整形态先设计、MVP 最小启用”的规则 | D04 必须写预留能力，不只写首版功能 |
| 状态命名不一致 | D08 统一状态全集和流转关系 | Draft、Candidate、Needs Review、Verified、Stable、Canonical、Deprecated、Rejected、Archived、Quarantined |
| 激励是否进入 MVP | 第一版页面和数据模型预留，现金收益不承诺 | D15 写账本和资格，D04 标注实现范围 |
| 企业能力是否首版实现 | 页面体现、对象预留、开发可后置 | D03/D13 写完整形态，D04 写首版裁剪 |
| 外部接入方式冲突 | 对话式自动接入优先，接入包 / Skill Pack、MCP、CLI、API 作为技术落地层 | D09 重写接入优先级 |
| 法务、收益、审核阈值不完整 | 标注待确认，不删除 | D13/D14/D15/D16 保留待确认项 |

## 10. 文档写作规则

6. 必须说明与其他文档的边界。

## 11. 待确认标记规则

后续文档中如遇无法根据现有资料和用户确认定稿的内容，必须使用统一标记。

| 标记 | 使用场景 |
|---|---|
| 【待确认】 | 内容方向存在，但细节需要用户确认 |
| 【需要用户确认】 | 存在多种可能处理方式，不能自行决定 |
| 【当前已读文档中未发现，需继续检查】 | 已读资料中未发现相关内容，不能判断项目不需要 |
| 【未完整读取，不能判断】 | 某文件未完整读取时使用；当前重构扫描阶段无此情况 |

示例：

| 场景 | 正确写法 |

## 12. 接入方式修正规则

旧文档中已有 MCP、CLI、API、SDK、Rules、Skills 等接入方式，但新的接入体验必须进一步调整。

快速接入不再只理解为：

1. 复制命令。
2. 执行 CLI。
3. 配置 MCP。
4. 手动理解 API。

新的快速接入优先理解为：

1. 用户复制一段接入指令给自己的 AI 编程工具。
2. AI 编程工具读取 Axiqra 接入描述、安装清单、Skill Pack 或等价文件。
3. AI 编程工具自动完成授权、配置、规则安装和环境检测。
4. AI 编程工具返回授权码或接入状态。
5. 用户在页面中确认绑定。
6. 后续任务开始前，AI 工具自动搜索 Axiqra。
7. 任务结束后，AI 工具根据规则生成 Draft Case，并等待用户确认。

该修正影响：

| 文档 | 影响 |
|---|---|
| D03 | 页面必须包含复制给智能体、接入包 / Skill Pack、授权码回填和接入状态 |
| D04 | MVP 需要实现真实可安装的对话式自动接入最小闭环，不只做模拟展示 |
| D06 | 数据模型需要增加接入会话、接入包 / Skill Pack、授权码和集成目标 |
| D09 | 接入协议需重写为对话式自动接入优先 |
| D10 | 技术架构需支持接入包分发、授权、安装检测和接入诊断 |
| D17 | 传播页面需把“复制给智能体即可接入”作为核心转化点 |

## 13. 规模化路线基准

后续技术和架构文档必须区分 MVP 实现栈和终局规模化路线。

| 阶段 | 定位 | 架构基准 | 不应误写为 |
|---|---|---|---|
| S0 | 原型 | 单体、本地 mock、本地索引或轻量后端 | 可生产承载 |
| S1 | MVP | 模块化单体、PostgreSQL、pgvector、Redis、MinIO、MCP、CLI、REST API | 终局架构 |
| S2 | 商业试点 | 独立搜索、独立向量、事件流、OLAP、租户分片 | 仍靠单库硬扛 |
| S3 | 平台化 | 多集群搜索、对象湖、流处理、专属租户、服务拆分 | 单一区域单索引 |
| S4 | 全球规模 | 多区域 Cell、联邦搜索、分层索引、自动容量治理 | 单一全球热索引 |

规模化写作要求：

1. `PostgreSQL + pgvector` 只能写为 S1 快速验证。
2. 面向千万到 1 亿级文档/用户规模，必须写搜索、向量、事件流、OLAP、租户分片和索引生命周期。
3. 面向百亿级 Chunk，必须写冷热分层、权限预过滤、索引回填、删除传播和评测门禁。
4. 不允许把全量内容都放进热向量索引。
5. 不允许先全局召回再应用层过滤权限。
