# Axiqra 测试用例流程规范

## 1. 文档目的
本文档用于规定 Axiqra 项目测试资料的组织方式、测试执行记录要求、测试报告归档方式以及复用模板的使用原则。

本文档目标如下：
- 建立团队级统一的测试文档规范；
- 明确测试资料的分层结构与分类边界；
- 统一测试执行记录的最小必填信息；
- 提升代码评审、回归验证与发布准备过程中的可追溯性。

## 2. 适用范围
本规范适用于 `axiqra-code` 下的工程测试资料管理，重点覆盖基于 Maven 的 Java 测试流程及其归档方式。

适用范围包括：
- `src/test/java` 下的测试类组织；
- 基于 Maven Surefire 的测试执行；
- `test-cases` 目录中的正式测试报告归档；
- 根据测试结果整理出的测试记录、commit message 与 Pull Request 测试说明。

## 3. 测试分类规范
当前项目遵循根构建配置中定义的 Maven 测试命名约定。

### 3.1 命名规则
- 单元测试或常规模块测试：`*Test.java`
- 集成测试：`*IT.java`
- 端到端测试：`*E2ETest.java`

### 3.2 Surefire 包含与排除规则
当前 Surefire 执行规则如下：
- 包含：`**/*Test.java`
- 排除：`**/*IT.java`
- 排除：`**/*E2ETest.java`

配置来源：
- `axiqra-code/pom.xml`

## 4. 测试资料分层规范
### 4.1 standards
用于存放测试规范、流程说明、记录要求与归档原则。

### 4.2 reports
用于存放正式归档的测试报告。

适用场景包括：
- 某次关键修复后的验证结论；
- 某一模块的阶段性测试结果；
- 发布前或回归阶段形成的正式留档记录。

### 4.3 templates
用于存放可复用模板。

建议优先提供以下类型模板：
- 测试执行记录模板；
- PR 测试计划模板；
- 提交测试说明模板。

### 4.4 inventories
用于存放测试资产清单、回归清单与发布检查项。

## 5. 测试报告归档规范
### 5.1 归档原则
构建过程产生的 `target` 目录属于临时目录，只用于本地构建与调试，不作为正式测试资料的长期存放位置。

正式测试报告应归档到：
- `axiqra-project/test-cases/reports/`

### 5.2 原始结果与正式报告的关系
测试执行后可能产生以下两类信息：
- 原始构建结果
  - 位于模块 `target/surefire-reports/`，用于本地执行校验与临时排错；
- 正式归档报告
  - 位于 `test-cases/reports` 目录，用于项目长期留档、评审与协作引用。

### 5.3 原始结果文件类型说明
在 `target/surefire-reports/` 下通常可见：
- `*.txt`
  - 面向人工快速查看的测试摘要；
- `TEST-*.xml`
  - 面向 CI、归档与自动化处理的标准 XML 报告；
- `*.dumpstream`
  - 测试异常、中断或排错过程中产生的辅助文件。

### 5.4 使用规则
在正式记录与评审场景中：
- 应以 `test-cases/reports` 目录中的归档报告作为正式引用对象；
- 不得将 `target` 目录下的临时文件直接视为正式项目文档；
- 不得将 `*.dumpstream` 作为测试通过证明；
- 除非明确要求，不应将原始 XML 或完整日志直接粘贴进项目文档。

## 6. 测试执行记录规范
新增正式测试记录时，至少应包含以下信息：
- 测试对象；
- 测试目标；
- 执行时间；
- 执行目录；
- 执行命令；
- 结果摘要；
- 归档位置；
- 原始结果来源。

若测试失败，还应补充：
- 失败现象；
- 初步原因判断；
- 后续处理动作。

## 7. 测试验证层级建议
### 7.1 定向验证
当本次变更仅影响单个测试类、单个接口或单个明确场景时：
- 优先执行最小必要验证；
- 命令应与修改范围直接对应；
- 结果应进入正式记录或 PR 测试计划。

### 7.2 模块级验证
当本次变更影响同一模块内多个文件、接口或配置时：
- 建议执行模块级测试；
- 确认模块范围内无明显回归；
- 必要时补充关键场景的定向验证。

### 7.3 项目级验证
当本次变更影响共享依赖、启动流程、根构建配置或跨模块行为时：
- 建议执行项目级测试；
- 必要时同步补充模块级或定向验证；
- 应在记录中说明验证范围与风险判断。

## 8. 模板与清单使用规则
### 8.1 模板使用
新增记录时，优先复用 `templates/` 下已有模板，而不是从零编写结构。

### 8.2 清单维护
新增测试类、测试场景、模块覆盖范围或发布检查项时，应同步更新 `inventories/` 下对应清单。

### 8.3 引用原则
在提交说明、PR 描述或评审沟通中，应优先引用归档后的正式文档，而不是引用临时构建输出。

## 9. 提交前测试资料检查
提交前至少确认以下事项：
- 本次变更对应的测试范围已经明确；
- 已选择与变更范围匹配的验证层级；
- 若形成正式测试结论，已归档到 `reports/`；
- 若新增测试类或测试场景，已同步更新相关清单；
- 不将 `target` 目录作为长期测试资料存放位置。

## 10. 维护规则
- 每新增一个测试类或测试场景，应同步补充到相关清单中；
- 每次关键验证执行后，应至少记录执行信息、结果摘要与正式归档路径；
- Pull Request 中应引用精简后的验证结论，不粘贴大段原始日志；
- `dumpstream` 等排错文件可用于辅助定位问题，但不得作为正式通过依据；
- 正式测试资料统一维护在 `test-cases` 分层目录内，不得长期依赖 `target` 目录保存项目测试记录。
