## 1. 文档定位

本文档定义 Axiqra 的 MVP 实施范围与版本路线。

这里的 MVP 不是低配产品，也不是把完整产品删到只剩几个页面。Axiqra 的 MVP 必须建立在完整产品形态之下：原型尽量完整，数据模型充分预留，工程闭环先跑通，复杂能力按阶段启用。

本文档回答以下问题：

1. 当前第一版必须真正实现哪些能力。
2. 哪些能力必须在完整原型中展示，但可以不在第一版完整开发。
3. 哪些能力必须在对象、状态、权限、索引、接入和日志中预留。
4. 哪些能力明确后置，但不能从产品体系中删除。
5. MVP 如何避免未来升级时再次重构。
6. 当前版本路线如何从原型、MVP、团队协作、企业可信、规模化生态逐步演进。

本文档不是产品定位文档、页面设计文档、技术架构文档、对象字段文档或治理制度文档。它只定义实施范围、裁剪边界、阶段路线和验收标准。

## 2. MVP 总原则

### 2.1 MVP 不是低配版

Axiqra 的 MVP 不能只做一个搜索页面、一个案例列表或一个简单知识库。按已确认定位，Axiqra 要验证的是工程方案记忆层是否成立，所以 MVP 必须至少跑通：

1. 人能读懂真实工程 Case 和 Solution。
2. AI 工具能通过接入方式调用 Solution。
3. 用户能把真实工程上下文沉淀为 Project Case。
4. 私有 Project Case 能经过脱敏、授权和审核进入 Public Case。
5. Solution 能带着适用边界、验证证据、风险等级和反馈记录持续演进。
6. 调用后能形成 worked、partial、failed、not_applicable 等反馈。
7. 搜索没有命中时能进入 Candidate Seed 或候选沉淀路径。
8. 团队、企业、治理、激励和规模化能力在页面和对象中有清晰预留。

如果第一版只实现静态展示，而没有真实接入、真实回传、真实发布、真实反馈或真实状态预留，就无法验证 Axiqra 的核心闭环。

### 2.2 完整原型先行，实施范围分层

D03 已确认完整原型必须尽量大而全，因为原型是理解、传播、试点、融资、团队沟通和反推数据模型的重要载体。

但完整原型不等于第一版所有能力都要工程化。D04 采用四层实施边界：

| 层级 | 含义 | 第一版要求 |
|---|---|---|
| 完整展示层 | 页面和原型必须看见完整产品方向 | 必须展示 |
| MVP 启用层 | 第一版必须真实可用的能力 | 必须开发 |
| 数据预留层 | 后续升级必须依赖的对象、字段、状态、权限、索引、日志 | 必须预留 |
| 后置实现层 | 复杂企业、现金收益、规模化搜索、自动治理等能力 | 可以后置，但不能删除 |

### 2.3 第一版必须保留终局升级通道

MVP 可以轻实现，但不能把未来升级空间堵死。第一版必须预留：

1. 多空间：个人空间、团队空间、企业空间、公共空间。
2. 多对象：Project Case、Public Case、Solution、Solution Version、Invocation、Feedback、Evidence、Source、Review、Reward Ledger。
3. 多状态：Draft、Candidate、Needs Review、Verified、Stable、Canonical、Deprecated、Rejected、Archived、Quarantined 等状态全集。
4. 验证等级：L0-L5 全集。
5. 风险等级：R0-R4 全集。
6. 接入资产：接入会话、接入包、安装目标、授权码、MCP 配置、CLI、API Key、doctor 结果。
7. 权限隔离：空间、角色、可见性、数据归属、审计日志。
8. 搜索预留：关键词、向量、标签、技术栈、版本、风险、权限预过滤、排序特征、评测样本。
9. 治理预留：审核、举报、复核、隔离、污染标记、来源可信度。
10. 激励预留：贡献账本、积分、权益、收益池资格，不写固定现金比例。

这些预留可以先不做复杂自动化，但字段、状态、日志和页面入口不能缺失。

### 2.4 人类可读和 AI 可调用必须同时存在

Axiqra 不是只给 AI 的向量库，也不是只给人看的文档站。MVP 必须同时验证两条主线：

| 主线 | MVP 必须具备的能力 |
|---|---|
| 人类学习 | Public Case、Solution 详情、执行模式、学习解释模式、证据、适用边界、失败路径、风险提示 |
| AI 调用 | 对话式自动接入、可安装接入包、MCP/CLI/API 最小调用、检索返回、调用日志、反馈回传 |

如果只做人类可读，无法证明 AI 工程记忆层成立。  
如果只做 AI 接口，无法完成传播、学习、信任建立和内容治理。

### 2.5 对话式自动接入必须真实可安装

首版接入不能只做“复制命令”的静态演示，也不能把接入局限为单一 Skill 形态。MVP 必须实现一个真实可安装、可检测、可回退的最小闭环：

1. 用户在 Axiqra 选择接入目标。
2. 平台生成可复制给智能体的接入指令。
3. 智能体或用户通过对话方式完成接入流程。
4. 接入流程生成或安装接入包、配置片段、MCP 配置、CLI 或 API Key。
5. 平台能进行授权码回填或状态确认。
6. doctor 能检测接入状态。
7. 接入成功后能完成一次真实查询或样例调用。

接入包可以包含 Prompt、Rule、MCP 配置、CLI 指令、API 配置、工具描述、兼容声明和回退路径。Skill Pack 只是接入包的一种可能形态，不是唯一形态。

### 2.6 收益池不写固定比例

旧资料和用户确认中存在收益池、贡献激励、权益和商业化方向。MVP 必须预留贡献账本、贡献积分、权益资格、收益池入口和商业化扩展字段。

但第一版不写固定现金分配比例，不承诺收益池分账公式。收益池的比例、资金来源、审批、财务合规和结算规则进入 D15，并且在商业化阶段再补充。

### 2.7 技术路线服务 MVP，不锁死终局

MVP 技术路线按已确认方向采用：

1. 前端：Vue 3。
2. 后端：Spring Boot 模块化单体。
3. 主数据库：PostgreSQL。
4. 向量能力：pgvector。
5. 缓存和会话：Redis。
6. 文件和证据存储：MinIO。
7. 接入层：MCP、CLI、REST API。

这条路线服务 S1/MVP 快速验证，不等于千万到 1 亿级规模的终局方案。D04 只要求第一版不堵死后续升级：搜索、向量、事件流、OLAP、租户分片、索引生命周期、多区域架构必须在 D11/D12 中有迁移通道。

## 3. 阶段定义

本文档用能力阶段描述路线，不用固定日期承诺。阶段名称后续可在 D18 文档维护规则中统一，但能力边界以本文为准。

| 阶段 | 阶段定位 | 核心目标 | 交付性质 |
|---|---|---|---|
| P0 完整原型 | 展示全集 | 把完整页面、完整空间、核心对象、接入体验、团队和企业方向展示出来 | 可演示原型 |
| S0 工程底座 | 开发准备 | 搭建代码、数据、权限、状态、接入和部署底座 | 可开发系统 |
| S1 MVP 最小闭环 | 首版启用 | 跑通搜索、Public Case、Solution、Project Case、对话式自动接入、反馈和基础审核 | 可试点产品 |
| S2 团队协作 | 团队复用 | 引入团队空间、Owner Review、团队 Project Case、内部 Solution 和贡献账本 | 团队版雏形 |
| S3 企业可信 | 企业隔离 | 引入租户、权限、审计、数据隔离、企业接入和私有内容治理 | 企业试点 |
| S4 规模化生态 | 大规模验证 | 搜索升级、向量服务拆分、事件流、OLAP、分片、多区域、生态接入和商业化 | 规模化平台 |

P0 可以先于 S1 完成，并且可以比 S1 展示更多内容。S1 必须从 P0 中选择最小真实闭环，但不能删除 P0 展示的长期方向。

## 4. MVP 成功标准

S1 MVP 成立，不以页面数量判断，而以闭环是否真实跑通判断。

### 4.1 产品闭环成功标准

| 闭环 | 成功标准 |
|---|---|
| 搜索闭环 | 用户能输入错误、技术栈、任务或关键词，得到 Public Case、Solution 或 Candidate Seed 路径 |
| 学习闭环 | 用户能阅读 Public Case 和 Solution，并区分执行模式、学习模式、证据和风险 |
| 沉淀闭环 | 用户能创建或导入 Project Case，保存上下文、过程、结果、证据和私有状态 |
| 发布闭环 | 用户能从 Project Case 发起脱敏发布，进入审核或候选池 |
| Solution 闭环 | Solution 能展示适用场景、边界、验证等级、风险等级、证据和调用方式 |
| AI 接入闭环 | 外部 AI 工具能通过真实安装方式完成至少一次检索或调用 |
| 反馈闭环 | 调用后能记录 worked、partial、failed、not_applicable，并进入统计和复核路径 |
| 治理闭环 | 内容能经过基础审核、拒绝、隔离或复核，不会未经授权直接进入公共空间 |
| 传播闭环 | 演示台、首页、搜索、案例和接入页能支持外部用户理解和试点 |

### 4.2 技术闭环成功标准

| 闭环 | 成功标准 |
|---|---|
| 前端闭环 | Vue 原型中的核心页面能进入可用系统，样式继承 D03 的视觉方向 |
| 后端闭环 | Spring Boot 模块化单体能支撑核心对象、检索、接入、反馈、审核和用户空间 |
| 数据闭环 | PostgreSQL 能保存核心对象，pgvector 能支持首版向量检索，字段具备后续升级预留 |
| 文件闭环 | MinIO 能保存日志片段、截图、证据、附件或导入包 |
| 缓存闭环 | Redis 能支撑接入会话、短期状态、限流或任务状态 |
| 接入闭环 | MCP/CLI/API 至少一条路径可真实运行，其他路径有清晰回退 |
| 日志闭环 | 调用、接入、审核、发布和反馈都有可追踪记录 |
| 部署闭环 | S1 能用轻量部署方式运行，后续可迁移到分布式架构 |

## 5. S1 MVP 必须实现的能力

### 5.1 首页、搜索和覆盖范围

| 能力 | MVP 要求 | 预留要求 |
|---|---|---|
| 首页 | 展示定位、搜索入口、热门问题、Solution / Case 入口、接入入口 | 保留传播页和商业验证入口 |
| 全站搜索 | 支持关键词、错误日志、技术栈、框架、版本等基本检索 | 预留多路召回、权限预过滤、排序特征和评测集 |
| 搜索结果 | 同时返回 Public Case、Solution 和无命中候选路径 | 预留团队、企业、私有结果混合搜索 |
| 覆盖范围页 | 展示已覆盖技术栈、低覆盖领域、Candidate Seed | 预留覆盖质量指标和种子任务 |
| 空结果 | 引导用户提交候选问题或创建 Project Case | 预留悬赏、众包、维护者认领 |

### 5.2 Public Case 和人类学习

| 能力 | MVP 要求 | 预留要求 |
|---|---|---|
| Public Case 列表 | 展示真实或授权种子内容，支持筛选和搜索 | 预留可信来源、贡献者、验证证据和排序指标 |
| Public Case 详情 | 展示问题、上下文、排查过程、失败路径、最终方案、证据和关联 Solution | 预留学习路径、讨论、争议和复盘 |
| 学习模式 | 用人类可读方式解释为什么这样解决、踩过哪些坑、适用边界是什么 | 预留课程化、团队复盘和学习积分 |
| 执行参考 | 可以跳转到关联 Solution 的执行模式 | 预留 AI 调用上下文 |
| 授权和脱敏标记 | 每个公开内容必须显示授权、脱敏和来源状态 | 预留更细的合规证明 |

### 5.3 Solution 和 AI 调用

| 能力 | MVP 要求 | 预留要求 |
|---|---|---|
| Solution 列表 | 展示标题、技术栈、状态、验证等级、风险等级、样本量、最近验证 | 预留多版本、分叉、融合和稳定推荐 |
| Solution 详情 | 展示适用场景、不适用场景、执行步骤、证据、风险、回滚提示和 AI 指令 | 预留分段执行、参数化调用和企业策略 |
| 执行模式 | 为 AI 或开发者提供清晰操作步骤 | 预留工具调用和自动化执行 |
| 学习模式 | 为人解释上下文和取舍 | 预留训练、复盘和团队知识库 |
| L0-L5 展示 | MVP 必须支持 L0-L5 枚举、展示、筛选和管理 | L3-L5 可先通过人工审核或种子数据展示，自动晋级后续增强 |
| R0-R4 展示 | MVP 必须支持风险等级和人工确认提示 | 高风险自动执行后置 |

### 5.4 Project Case 和个人空间

| 能力 | MVP 要求 | 预留要求 |
|---|---|---|
| 个人空间 | 展示我的项目、Project Case、存储、接入状态、API Key | 预留团队、企业和私有数据隔离 |
| Project Case 创建 | 支持手动创建、粘贴日志、填写环境、过程、结果、证据 | 预留 IDE/AI 自动回传 |
| Project Case 详情 | 展示完整私有上下文、附件、证据、关联 Solution、发布状态 | 预留团队协作、审计和版本 |
| 脱敏发布 | 支持从 Project Case 发起 Public Case 候选 | 预留自动脱敏、人工复核和多级审核 |
| 导入导出 | MVP 至少保留导入导出入口或基础导出 | 预留历史数据迁移和批量导入 |

### 5.5 对话式自动接入

| 能力 | MVP 要求 | 预留要求 |
|---|---|---|
| 复制给智能体 | 生成一段可复制给外部 AI 工具的接入指令 | 预留多工具模板和上下文检测 |
| 接入会话 | 平台创建接入 session，记录目标工具、用户、权限、过期时间和状态 | 预留团队和企业策略 |
| 接入包 | 生成或分发可安装接入包，包含 Prompt、Rule、MCP、CLI、API 配置等 | Skill Pack 作为一种形态保留，不作为唯一形态 |
| 授权码回填 | 支持用户或智能体完成授权确认 | 预留 OAuth、企业 SSO 和设备码 |
| doctor 自检 | 检测配置、网络、鉴权、版本、可用接口 | 预留自动修复建议 |
| 示例调用 | 接入完成后执行一次真实检索或样例调用 | 预留调用日志和反馈自动回传 |
| 降级路径 | MCP 不可用时能使用 CLI 或 REST API | 预留更多插件和 SDK |

### 5.6 调用日志和反馈

| 能力 | MVP 要求 | 预留要求 |
|---|---|---|
| Invocation | 记录 AI 或人调用了哪个 Solution、在哪个上下文、结果如何 | 预留企业审计和匿名统计 |
| Feedback | 支持 worked、partial、failed、not_applicable | 预留加权有效率、降级和复核队列 |

## 10. 对话式自动接入的 S1 最小闭环

为了避免快速接入变回传统静态文档或硬编码 CLI 命令复制，S1 必须将 **“智能体对话引导与本地 Doctor 网桥自检”** 组合定义为首发 MVP (S1) 的核心 Onboarding 闭环。

> [!IMPORTANT]
> **S1 极速 Onboarding 闭环标准：**
> * **对话安装指令 (Command Dispatcher)**：用户复制一段结构化的引导文本给 Agent（Cursor/Claude Code）。该指令命令 Agent 自动通过 HTTP 或本地 CLI 读取平台的集成 manifest 文件。
> * **本地 Doctor 网桥自检 (Diagnose Tunnel)**：用户在本地终端或页面端激活 `doctor 自检`，触发本地同步网桥自测。终端以跑马灯格式串行打印如下 8 条日志以证明网络、API Key 和脱敏引擎正则规则已全线绿灯就绪，拒绝使用纯静态 UI 占位图。

### 10.1 首版接入链路

S1 至少实现以下链路：

1. 用户进入接入页。
2. 用户选择目标 AI 工具或通用接入方式。
3. Axiqra 生成一段“复制给智能体”的接入指令。
4. 智能体根据指令请求或使用 Axiqra 的接入包。
5. Axiqra 创建接入会话并生成授权码、API Key 或配置片段。
6. 智能体或用户完成本地配置。
7. doctor 检测连接状态并返回包含 8 行标准的连接诊断成功日志。
8. 智能体执行一次检索或调用。
9. Axiqra 记录接入状态、调用日志和结果。
10. 失败时给出 MCP、CLI、REST API 或手动配置的回退路径。

### 10.2 首版接入目标和接入通道

首版不再按“只选择一个 AI 工具”来理解接入目标。用户已确认：凡是能够通过 Rules、MCP、Skill、API、SDK 等方式接入的工具和形态，都应纳入 Axiqra 的接入体系。

因此，S1 的接入目标分成两层：

1. 接入通道层：Rules、MCP、Skill、API、SDK、CLI、接入包 manifest、复制给智能体的对话指令。
2. 目标工具层：Codex、Claude Code、Cursor、通用 MCP 客户端、Axiqra CLI、REST API 调用方，以及后续支持同类接入方式的外部 AI 工具。

S1 不应把接入写成“只接一个工具”。它至少要真实跑通一条安装链路，同时建立兼容矩阵和接入包抽象，让所有可接入形态能够逐步进入同一套接入体系。

可选目标和通道包括：

| 目标 | 优点 | 风险 |
|---|---|---|
| Codex / Claude Code 类命令行智能体 | 适合复制给智能体和 CLI / MCP 配置 | 需要明确本地配置路径和权限 |
| Cursor 类 IDE 智能体 | 传播价值高，面向开发者直接 | 插件和规则接入方式可能变化 |
| 通用 MCP 客户端 | 协议相对清晰，利于多工具复用 | 用户理解成本较高 |
| Axiqra CLI | 可控性强，便于 doctor 和降级 | 需要额外安装分发 |
| REST API + API Key | 最稳定，便于调试 | 不够“对话式自动接入” |
| Rules / Prompt 规则 | 适合快速复制给智能体或 IDE | 能力边界依赖目标工具 |
| Skill / Skill Pack | 适合打包特定工具的接入资产 | 不能作为唯一接入形态 |
| SDK | 适合后续开发者和企业深度集成 | S1 可先定义方向，完整实现后置 |

当前建议：S1 以“复制给智能体 + 接入包 manifest + Rules / MCP / Skill / API / SDK 接入能力矩阵 + 至少一条真实安装链路 + REST API / CLI 回退”为最小实现。D09 需要进一步定义每种接入通道的协议、安装流程、兼容条件、权限边界和降级路径。

### 10.3 接入包最小内容

S1 接入包至少包含：

1. 目标工具类型。
2. 接入包版本。
3. Axiqra 服务地址。
4. 授权方式。
5. MCP 配置或 CLI 命令。
6. 可复制 Prompt / Rule。
7. 查询接口说明。
8. 反馈回传接口说明。
9. doctor 检查项。
10. 回退路径。
11. 卸载或禁用说明。
12. 安全提示和权限边界。

接入包可以导出为文件、配置片段或对话指令。Skill Pack 是接入包可导出的形态之一，不是接入协议本身。

## 11. 搜索与内容冷启动范围

### 11.1 S1 搜索范围

S1 搜索必须能覆盖：

1. Public Case。
2. Solution。
3. 技术栈和版本。
4. 错误关键词。
5. 适用场景。
6. 风险等级。
7. 验证等级。
8. 来源类型。
9. 最近验证或更新时间。
10. 空结果 Candidate Seed。

S1 搜索可以采用 PostgreSQL 全文检索、结构化筛选和 pgvector 的轻量组合。该实现必须保留迁移到独立搜索和向量服务的通道。

### 11.2 冷启动内容范围

公开内容是团队冷启动和传播基础，但必须满足授权、脱敏、审核和可信来源标记。

S1 不追求海量内容，而是建立第一批授权清楚、来源可信、可验证、可调用、可治理的种子 Solution。S1 的目标不是开放内容大爆发，而是可信种子冷启动。

### 11.3 S1 种子内容总体数量

S1 第一轮冷启动建议按 8-12 周组织。

| 内容类型 | S1 建议数量 |
|---|---:|
| Project Case / Engineering Case | 300-500 条 |
| Public Case | 150-250 条 |
| Candidate Solution | 80-120 条 |
| L2+ Verified Solution | 40-60 条 |
| L3 Solution | 15-25 条 |
| L4 Solution | 3-8 条 |
| L5 Solution | S1 不强求，原则上可以没有 |

这个数量目标用于验证以下闭环：

1. AI 工具能查到 Solution。
2. Solution 有真实上下文。
3. Solution 有授权来源。
4. Solution 有验证证据。
5. Solution 能被反复调用。
6. 调用结果能 worked / failed 回传。
7. 多个 Case 能融合成更强的 Solution。
8. 低质量内容不会污染核心库。

S1 如果一开始追求几千条内容，很容易变成低质堆积。如果只有十几条内容，又无法验证搜索、调用、回传、融合和升级闭环。因此 S1 以 80-120 条 Candidate Solution、40-60 条 L2+ Verified Solution 作为合理起步目标。

### 11.4 S1 授权来源

S1 种子内容来自 5 类来源。

| 来源 | Case 数量 | Solution 数量 | 目标等级 | 是否默认公开 |
|---|---:|---:|---|---|
| 官方种子 | 80-120 | 40-60 | L1-L2，少量 L3 | 可公开 |
| Axiqra Dogfooding | 80-120 | 20-30 | L1-L3 | 可选择公开 |
| 早期可信开发者 | 100-200 | 30-50 | L1-L3 | 用户选择 |
| 企业试点空间 | 100-250 | 20-50 | 企业内部 L2-L4，公共空间 L1-L3 | 默认私有 |
| 受控社区贡献 | 80-150 | 10-20 | Draft / Candidate 为主 | 审核后公开 |

### 11.5 官方种子 Solution

官方种子是 S1 的内容骨架。

来源包括：

1. 平台团队原创整理。
2. 核心开发者整理。
3. 认证专家参与编写。
4. 官方根据真实工程经验重写。
5. Axiqra 团队自有项目经验沉淀。

授权要求：

1. 平台自有版权。
2. 平台员工或合作作者明确授权。
3. 专家共创内容签署贡献协议。
4. 不得直接搬运第三方文章、论坛、博客原文。

建议数量：

1. 官方种子 Solution：40-60 条。
2. 关联 Case：80-120 条。
3. 目标等级：L1-L2 为主，少量 L3。

官方种子用于建立内容质量样板、定义 Solution 结构、覆盖最高频工程场景，并给搜索和 AI 调用提供第一批可信内容。官方种子不能因为是官方编写就直接标为 L4 / L5，必须经过真实调用反馈才能升级。

1. Axiqra 自有项目经验默认可进入私有 Project Case。
2. 脱敏后可生成 Public Case。
3. 可聚合成官方 Solution。

建议数量：

1. Dogfooding Engineering Case：80-120 条。
2. 可形成 Solution：20-30 条。
3. 目标等级：L1-L3。

Dogfooding 的作用是自己先用、自己先验证自动回传、自己先验证 Solution 融合、自己先发现数据模型问题，并证明 Axiqra 不是纸面产品。

### 11.7 早期可信开发者

早期可信开发者是 S1 的外部可信来源。

对象包括：

1. AI 重度开发者。
2. 中高级后端开发者。
3. 独立开发者。
4. 开源项目维护者。
5. Tech Lead。
6. 小团队负责人。
7. 经常使用 Cursor / Claude Code / Codex 的真实用户。

授权要求：

1. 签署贡献者授权协议。
2. 允许保存私有 Project Case。
3. 用户可选择是否生成 Public Case。
4. 用户可选择是否参与 Solution 聚合。
5. 用户可选择是否允许匿名统计。
6. 用户可选择是否参与未来收益池。

建议数量：

1. 早期可信开发者：30-50 人。
2. 每人贡献真实 Case：3-5 条。
3. Engineering Case：100-200 条。
4. 可形成 Solution：30-50 条。
5. 目标等级：L1-L3。

个人开发者不等于低可信。如果一个独立开发者有真实线上项目、日志、测试记录、部署记录，他的 Case 可以成为可信工程来源。

### 11.8 企业试点空间

企业试点空间是高可信私有记忆来源。

对象包括：

1. 早期企业客户。
2. 小型研发团队。
3. 外包交付团队。
4. SaaS 团队。
5. 有内部 AI Agent 的研发团队。
6. 有大量重复工程方案的技术团队。

授权要求：

1. 默认企业私有。
2. 默认不公开。
3. 默认不参与训练。
4. 默认不进入公共 Solution。
5. 企业可选择匿名统计。
6. 企业可选择脱敏贡献。
7. 企业可选择只贡献失败路径。
8. 企业可选择只贡献通用 Solution 片段。
9. 企业可选择参与评测集或数据授权。

建议数量：

1. 企业试点空间：3-5 个。
2. 每个企业空间 Project Case：30-60 条。
3. 企业私有 Case：100-250 条。
4. 可形成企业内部 Solution：20-50 条。
5. 可脱敏贡献公共 Solution：5-15 条。
6. 目标等级：企业内部 L2-L4，公共空间 L1-L3。

企业空间的内容不一定公开，但可能比公开社区内容更可信。S1 必须验证企业空间、私有高可信记忆、权限隔离、可信调用方和企业内部 Solution。

### 11.9 受控社区贡献

S1 可以开放一小部分社区贡献，但必须受控。

对象包括：

1. 普通开发者。
2. 新人开发者。
3. 学习型用户。
4. 社区志愿贡献者。
5. 公开案例补充者。

授权要求：

1. 提交时必须选择 license_scope。
2. 默认进入 Draft / Candidate。
3. 默认不进入高可信推荐。
4. 默认不参与训练。
5. 公开前必须脱敏。
6. 参与收益池需要额外授权。
7. 参与数据授权需要单独授权。

建议数量：

1. 社区 Candidate Case：80-150 条。
2. 进入 Reviewed Public Case：30-60 条。
3. 进入 Candidate Solution：10-20 条。
4. 进入 L2+ Verified Solution：不强求，可能只有 3-8 条。

S1 的社区贡献重点不是产出高可信 Solution，而是验证社区入口、垃圾隔离、新人贡献路径、认证开发者审核和 Draft -> Candidate -> Reviewed -> Verified 流程。

### 11.10 S1 必须记录的授权字段

每条 Case / Solution 都必须记录授权来源。

建议 D06 至少定义以下字段：

```text
source_type：来源类型
source_owner：来源所有者
contributor_user_id：贡献者
workspace_id：所属空间
authorization_type：授权类型
license_scope：授权范围
visibility_scope：可见范围
usage_scope：可用范围
training_allowed：是否允许训练
eval_allowed：是否允许评测
commercial_allowed：是否允许商业使用
public_allowed：是否允许公开
solution_merge_allowed：是否允许参与 Solution 融合
reward_eligible：是否参与贡献者收益
redaction_status：脱敏状态
evidence_refs：验证证据引用
provenance_note：来源说明
```

`license_scope` 至少需要包含：

```text
private_only：仅个人私有
team_only：仅团队内部
enterprise_only：仅企业内部
anonymous_stats_only：仅允许匿名统计
public_case_allowed：允许生成 Public Case
solution_merge_allowed：允许参与 Solution 聚合
eval_only：允许进入评测集
training_allowed：允许训练使用
commercial_allowed：允许商业授权
```

默认策略必须保守：

1. 个人 / 企业私有内容默认 private_only 或 enterprise_only。
2. 不默认公开。
3. 不默认训练。
4. 不默认商业使用。
5. 不默认参与公共 Solution。
6. 必须由用户或企业明确授权。

### 11.11 S1 场景覆盖建议

S1 不只做排障，但可以从高频工程方案开始。

建议覆盖 10 类高频场景：

1. Docker / Docker Compose / 容器网络。
2. Redis / 缓存 / 连接配置。
3. PostgreSQL / MySQL / 数据库连接、迁移、索引。
4. Nginx / OpenResty / 网关 / 反向代理。
5. Spring Boot / Java 后端常见工程方案。
6. CI/CD / GitHub Actions / 构建部署。
7. Kubernetes / 服务编排基础问题。
8. 权限 / JWT / OAuth / 安全加固。
9. 技术选型 / 架构取舍 / 模块化单体与微服务。
10. 功能交付 / 测试方案 / 文档方案。

每类建议：

1. Candidate Solution：8-12 条。
2. L2+ Verified Solution：4-6 条。
3. L3 Solution：1-3 条。

### 11.12 为什么 S1 不强求 L5

L5 至少需要 15 次适用调用、5 个独立工程上下文、2 类来源类型、长期没有严重 failed、持续维护，并覆盖跨环境、跨版本、跨产品阶段验证。

S1 是冷启动阶段，不应该强行制造 L5。如果 S1 出现大量 L5，可能说明标准太松、样本造假、把官方种子误标成高可信，或者把专家经验误当成长期验证。

S1 最健康的状态是：大量 L1-L2，一部分 L3，极少量 L4，基本没有 L5。

### 11.13 S1 内容冷启动验收

S1 不以“内容很多”为验收标准。S1 的内容验收标准是：

1. 至少 80 条 Candidate Solution。
2. 至少 40 条 L2+ Verified Solution。
3. 至少 15 条 L3 Solution。
4. 至少 300 条真实 Engineering Case。
5. 至少 30 名早期可信开发者参与。
6. 至少 3 个企业试点空间接入。
7. 至少 5 类高频工程场景覆盖。
8. 每条 Solution 都有 license_scope。
9. 每条 Public Case 都完成脱敏。
10. 每条 L2+ Solution 都有验证证据。
11. 每条 L3+ Solution 都有独立工程上下文。
12. 所有社区内容默认不进入高可信推荐。
13. 企业内容默认私有。
14. 可以完成一次完整闭环：调用 -> 执行 -> 回传 -> 融合 -> 升级。

S1 种子内容策略可以归纳为：不靠开放投稿堆数量，而靠官方种子、Dogfooding、早期可信开发者、企业试点空间和受控社区贡献，建立 300-500 条真实 Engineering Case、80-120 条 Candidate Solution、40-60 条 L2+ Verified Solution，先跑通可信工程方案记忆闭环。

## 12. 验证等级、风险等级和反馈的 S1 范围

### 12.1 验证等级范围

S1 必须支持 L0-L5 的完整展示和数据预留，但真实样本不足时不能夸大等级。

| 等级 | S1 处理方式 |
|---|---|
| L0 | 必须支持，用于草稿、候选、未验证内容 |
| L1 | 必须支持，用于用户确认有效的真实 Project Case |
| L2 | 必须支持，用于具备客观证据的内容 |
| L3 | 支持展示、种子展示和真实上架，具体采用人工标注还是 AI 辅助标注待后续问答单确认 |
| L4 | 支持展示、筛选、字段和说明，真实晋级需足够样本 |
| L5 | 支持展示、筛选、字段和说明，不得解释为绝对正确 |

S1 不要求一上线就自然产生大量 L4/L5 内容，但必须让系统能够表达、管理和后续生成这些等级。

### 12.2 风险等级范围

S1 必须支持 R0-R4，并在页面和 AI 调用中体现人工确认要求。

| 风险等级 | S1 处理方式 |
|---|---|
| R0 | 可阅读、可解释、可低风险引用 |
| R1 | 可推荐，执行前提示低风险 |
| R2 | 推荐前需要用户确认 |
| R3 | 高风险，必须人工确认或领域审核 |
| R4 | 极高风险，只能作为审查参考，不允许 AI 自动执行 |

### 12.3 反馈范围

S1 必须支持四类反馈：

| 反馈 | S1 处理 |
|---|---|
| worked | 记录有效调用和证据 |
| partial | 记录部分有效，需要拆分有效和无效步骤 |
| failed | 进入复核或边界整理 |
| not_applicable | 不算失败，但必须更新不适用边界 |

S1 不需要完全自动降级，但必须记录足够数据，保证 D08 后续可以实现自动降级。

| 接入可诊断 | doctor 能检测成功、失败和降级路径 |
| 搜索可重建 | 索引元数据可追踪，后续可迁移 |
| 日志可审计 | 发布、审核、调用、反馈、接入有日志 |
| 文件可管理 | 证据和附件能保存、引用和删除 |
| 权限不穿透 | 私有 Project Case 不会被公共搜索直接命中 |
| 部署可复现 | 本地或测试环境可稳定部署 |
| 后续不重构 | S2/S3/S4 关键对象不需要推倒重来 |

### 18.3 内容验收

| 验收项 | 通过标准 |
|---|---|
| 种子内容 | 建立 300-500 条真实 Engineering Case、80-120 条 Candidate Solution、40-60 条 L2+ Verified Solution |
| 内容来源 | 每条公开内容有来源类型和授权状态 |
| 验证状态 | 大量 L1-L2、一部分 L3、极少量 L4，S1 不强求 L5，不把低样本伪装成高可信 |
| 风险提示 | 中高风险内容有明确人工确认提示 |
| 失败路径 | 至少能展示 failed / partial 对边界的影响 |
| 学习价值 | Case 不只是结果，还包含过程和取舍 |

## 19. 版本裁剪规则

如果开发资源不足，裁剪顺序必须遵守以下规则。

### 19.1 不能裁剪

1. 搜索。
2. Public Case。
3. Solution。
4. Project Case。
5. 对话式自动接入真实安装最小闭环。
6. Invocation / Feedback。
7. 基础审核和脱敏。
8. 空间、状态、验证等级、风险等级、接入对象的数据预留。
9. 个人空间。
10. 冷启动种子内容。

### 19.2 可以降低实现深度

1. 团队空间后端可以先轻量实现，但完整可点击原型不能裁剪。
2. 企业空间复杂能力可以灰态，但必须详细展示能力边界。
3. 贡献者权益可以先记账不结算。
4. L3 以上可以先展示、种子展示和真实上架；人工标注还是 AI 辅助标注待后续问答单确认，自动晋级后置。
5. 复杂搜索排序可以先采用轻量规则。
6. 社区仲裁可以先留入口和状态。
7. 私有化部署可以先写预留，不实际交付。
8. 多 AI 工具接入可以先做一个真实目标，再扩展。

### 19.3 不能以裁剪名义删除

1. 团队和企业方向。
2. 收益池和贡献激励方向。
3. 审核、授权、脱敏和污染隔离。
4. L0-L5 和 R0-R4。
5. Solution 版本、融合、分叉和废弃预留。
6. 接入包抽象。
7. 搜索升级和架构迁移通道。

## 20. 风险与应对

| 风险 | 影响 | S1 应对 |
|---|---|---|
| MVP 做得太窄 | 后续升级变成补丁和重构 | 保留完整对象、状态、页面和接入预留 |
| MVP 做得太重 | 首版迟迟无法上线 | 区分展示、启用、预留和后置 |
| 接入只做演示 | 无法证明 AI 调用闭环 | 首版必须真实可安装 |
| 低样本成功率误导 | AI 和用户误判方案可信度 | 小样本不显示夸张百分比 |
| 公开内容污染 | 低质或未授权内容影响信任 | 授权、脱敏、审核、来源标记和隔离 |
| 企业数据泄露 | 破坏企业可信基础 | 默认私有，公共化必须授权 |
| 收益规则过早固定 | 后续商业化受限 | 不写固定比例，只做账本和资格 |
| 技术栈锁死终局 | 大规模时难迁移 | D11/D12 保留升级通道 |
| 页面展示和实现混淆 | 用户误解第一版承诺 | 页面标注状态，D04 明确范围 |

## 22. 当前结论

D04 的核心结论是：

1. Axiqra MVP 不是低配知识库，而是在完整工程记忆层形态下启用最小真实闭环。
2. 完整原型必须尽量完整，团队、企业、治理、激励、接入、学习和规模化方向都要可见。
3. S1 必须真实实现搜索、Public Case、Solution、Project Case、对话式自动接入、调用反馈和基础审核。
4. S1 必须预留空间、权限、状态、验证等级、风险等级、接入包、收益池、治理、搜索和规模化升级。
5. S1 接入不按单一工具理解，凡可通过 Rules、MCP、Skill、API、SDK 接入的形态都需要纳入接入体系。
6. S1 种子内容以可信冷启动为目标，建立 300-500 条 Engineering Case、80-120 条 Candidate Solution、40-60 条 L2+ Verified Solution，不追求开放投稿堆量。
7. S1 可以后置复杂企业、现金收益分配、自动仲裁、大规模搜索集群和 P6 自研 Agent。
8. 第一版必须避免未来扩展只能靠补丁增加，否则会重新走向重构。

本文档确认后，D05 将继续定义用户、AI Agent 与人类学习的双主线流程。
