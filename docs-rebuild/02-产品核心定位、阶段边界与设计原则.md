## 2. 产品核心定义

Axiqra 是面向 AI 编程工具、开发者和团队的工程方案记忆层。

它把真实工程任务中的问题、上下文、排查过程、失败路径、验证证据、修复方案和后续反馈，沉淀为可被 AI 调用、可被人学习、可被团队复用、可持续验证和演进的工程记忆资产。

这里的 AI 编程工具，指 Cursor、Claude Code、Codex、OpenClaw、企业自研 Agent 等能够参与代码生成、工程排查、架构讨论或开发协作的外部智能体工具。Axiqra 当前阶段不替代这些工具，而是为这些工具提供可检索、可验证、可追踪的工程记忆。

### 2.1 一句话定位

Axiqra 是外部 AI 编程工具、人类开发者和团队共同使用的工程方案记忆层。

它不只是保存文档，而是沉淀真实工程过程；不只是给人阅读，而是让 AI 在执行工程任务前可以先调用历史方案；不只是保存成功结果，而是保留失败路径、适用边界、验证证据和后续反馈。

### 2.2 核心命题

Axiqra 要解决的核心问题不是“开发者缺少又一个知识库”，而是：

1. AI 编程工具在不同项目中反复从零推理同类工程问题。
2. 团队真实解决过的问题没有变成可复用工程资产。
3. 工程方案缺少上下文、失败路径、验证证据和适用边界。
4. 人类开发者越来越依赖 AI 输出，但缺少可学习、可复盘的真实工程过程。
5. 高质量工程经验无法被长期归因、激励和治理。
6. 企业内部工程记忆难以在权限、安全和审计边界内被 AI 调用。

Axiqra 的产品重点不是“给 AI 更多文本”，而是让 AI 和人都能使用经过结构化、脱敏、验证、治理和持续反馈的工程方案记忆。

### 2.3 核心价值对象

Axiqra 同时服务四类对象。

| 对象 | 核心价值 |
|---|---|
| 外部 AI 编程工具 | 在执行工程任务前检索历史方案，减少从零推理，获取适用边界、验证方式和风险提示 |
| 人类开发者 | 阅读真实工程排查过程，理解失败路径、根因判断、修复验证和工程思维 |
| 团队与企业 | 把团队踩过的坑、做过的方案和验证过的经验变成可被新人和内部 AI 调用的工程资产 |
| 贡献者与维护者 | 让高质量工程经验被记录、归因、审核、维护，并在未来获得积分、权益或收益池资格 |

## 3. Axiqra 是什么

### 3.1 Axiqra 是工程方案记忆层

Axiqra 关注的是工程方案，而不是单个知识点。

一个工程方案通常包含：

1. 问题发生的真实上下文。
2. 技术栈、版本、环境、团队或业务约束。
3. 已尝试但失败的方向。
4. 排查时间线和证据链。
5. 根因判断。
6. 修复方案。
7. 验证方式。
8. 适用边界和不适用边界。
9. 风险、副作用和回滚方式。
10. 后续调用反馈。

因此，Axiqra 不回答“某个技术好不好”这类泛问题，而是沉淀“在什么产品阶段、什么团队规模、什么技术栈、什么约束下，某个方案为什么适合或不适合”的工程判断。

### 3.2 Axiqra 是 AI 可调用的 Solution 网络

Solution 是 Axiqra 中面向 AI 调用的核心方案单元。

外部 AI 工具在执行任务前，应能从 Axiqra 获得：

1. 候选 Solution。
2. 适用场景。
3. 不适用场景。
4. 前置条件。
5. 推荐执行步骤。
6. 验证标准。
7. 风险和回滚提示。
8. 关联 Case。
9. 验证等级。
10. worked / failed 反馈统计。

Solution 不是静态文章。它应能被调用、反馈、升级、融合、分叉、废弃、归档和重新排序。

Solution 的状态全集、验证等级、融合和分叉规则不在本文档展开，进入 D08。

### 3.3 Axiqra 是人类可读的工程学习系统

Axiqra 不是只给 AI 用。

对人类开发者来说，Public Case 是学习真实工程过程的主要入口。它不应该只展示“最终答案”，而应展示：

1. 问题现场。
2. 为什么这个问题容易误判。
3. 排查时间线。
4. 被排除的错误方向。
5. 关键证据。
6. 真正根因。
7. 修复和验证。
8. 工程思维总结。
9. 相似问题的迁移思路。

因此，Axiqra 的第一阶段必须同时保留 AI 调用主线和人类学习主线。人类可读内容不是后续附加能力，而是产品传播、冷启动、可信建立和开发者成长的基础。

### 3.4 Axiqra 是团队和企业的工程记忆底座

团队和企业的工程经验通常散落在 Issue、PR、聊天记录、Wiki、事故复盘、内部文档和 AI 会话中。

Axiqra 要让这些经验在权限、安全和审计边界内变成：

1. 团队 Project Case。
2. 团队内部 Solution。
3. 团队 Prompt / Rule / 接入包 / Skill Pack。
4. 企业私有工程记忆。
5. 内部 AI 工具可调用的可信资产。
6. 新人学习路径。
7. 可导出、可迁移、可删除、可审计的数据资产。

团队和企业能力在完整产品形态中必须存在。MVP 可以分阶段实现，但页面、对象模型和架构必须预留，不能等以后以补丁方式添加。

### 3.4.1 Axiqra 的默认产品气质是开放互联网级 SaaS

团队和企业能力很重要，但它们不是 Axiqra 的唯一主语。

Axiqra 的默认产品气质必须是：

```text
面向全球开发者、AI 工具用户、开源维护者、社区、小团队、企业和大集团的开放互联网级 SaaS 工程记忆层。
```

因此，页面、文案、原型和传播材料必须优先让以下用户觉得“我现在就可以用”：

1. 个人开发者。
2. AI 编程工具重度用户。
3. 开源维护者。
4. 社区贡献者。
5. 小团队。
6. 初创团队。

企业和大集团能力应作为成长路径中的高级阶段出现：

```text
个人开发者 -> 小团队 / 团队 -> 企业 -> 大集团
```

不能把首页、公开页面和原型前几屏写成企业后台、内部知识库、权限控制台或安全合规系统。

正确主线是：

```text
一个开发者修过的问题，可以变成下一次 AI Agent 可调用的工程经验。
一个团队反复踩过的坑，可以变成团队共享的 Solution。
一个企业验证过的工程方案，可以变成可信、可审查、可治理的工程记忆。
一个大集团跨项目积累的经验，可以变成跨组织、跨 Agent 的工程智能资产。
```

这条规则影响 D03 首页原型、D17 传播页面和后续所有公开产品文案。

### 3.5 Axiqra 是工程知识质量和可信治理系统

Axiqra 中的内容可能被 AI 用于真实工程任务，因此不能按普通内容社区处理。

Axiqra 必须从第一阶段开始建立：

1. 内容来源分层。
2. 脱敏和授权。
3. 结构校验。
4. 相似度查重。
5. 质量评分。
6. 验证等级。
7. 审核机制。
8. 风险隔离。
9. 污染防护。
10. 举报和申诉。
11. 贡献反作弊。
12. AI 消费侧保护。

可信治理的详细制度进入 D14 和 D16。

### 3.6 Axiqra 是贡献者归因和长期激励系统

真实工程方案来自开发者、团队和企业。高质量贡献不应只被平台消费，还应被记录、归因、维护和激励。

Axiqra 需要记录：

1. 谁贡献了 Case。
2. 哪个 Solution 被调用。
3. 哪次调用有效。
4. 哪次调用失败。
5. 哪个 Prompt / Rule / Skill 被复用。
6. 哪些内容被企业采用。
7. 哪些内容进入评测集。
8. 哪些内容具备未来收益资格。
9. 哪些内容因低质、重复、抄袭、未授权或脱敏失败而不具备资格。

贡献者激励第一版只写机制、账本、资格、反作弊和未来分配原则，不写固定比例和现金承诺。详细制度进入 D15。

## 4. Axiqra 不是什么

### 4.1 Axiqra 不是普通知识库

普通知识库保存文档、问答、笔记或经验片段。

Axiqra 保存的是带上下文、失败路径、验证证据、适用边界和调用反馈的工程方案记忆。它必须能被 AI 调用，也必须能被人理解。

### 4.2 Axiqra 不是提示词库

Axiqra 会沉淀 Prompt、Rule、Skill Pack 等提示资产，但提示词不是产品主定位。

Prompt / Rule / 接入包 / Skill Pack 在 Axiqra 中必须和真实 Case、Solution、调用反馈、验证结果绑定。它们不是静态模板，而是工程执行资产的一部分。

### 4.3 Axiqra 不是技术论坛或开放灌水社区

Axiqra 不能只依靠开放投稿堆积内容。

第一阶段的数据来源应以官方种子、平台自用、早期可信用户、小团队试点、企业授权数据和受控社区贡献为主。公开内容必须经过授权、脱敏、审核和质量治理。

### 4.4 Axiqra 不是排障执行平台

Axiqra 不直接执行修复、测试、部署、数据库迁移、权限变更、生产发布或删除操作。

外部 AI 编程工具或人类开发者负责执行。Axiqra 负责提供历史方案、适用边界、证据结构、验证标准和回传沉淀入口。

### 4.5 Axiqra 不是新的 AI 编程工具

当前阶段 Axiqra 不替代 Cursor、Claude Code、Codex、OpenClaw 或企业自研 Agent。

Axiqra 的当前阶段是让这些工具拥有可调用的工程记忆。未来是否探索自研 Agent，必须建立在工程记忆资产、接入生态、可信治理和企业需求成熟之后。

### 4.6 Axiqra 不是默认训练数据交易平台

Axiqra 可以沉淀工程数据、评测数据和授权数据，但不能默认把用户、团队或企业数据用于训练、出售或公开。

任何数据授权、评测集使用、商业合作和收益分成都必须基于明确授权、范围声明、反作弊和法务边界。相关内容进入 D13、D14、D15、D17。

### 4.7 Axiqra 不是自动公开平台

Project Case 默认属于个人、团队或企业空间。它不能自动变成 Public Case。

公开需要满足：

1. 用户或企业授权。
2. 脱敏。
3. 质量检查。
4. 审核。
5. 可见范围确认。
6. 必要时进行风险隔离。

### 4.8 Axiqra 不是“成功率越高越可信”的排行榜

成功率可能被样本量、来源、场景复杂度、调用方可信度和刷量行为影响。

Axiqra 的可信判断必须优先考虑验证等级、证据质量、样本量、审核者身份、场景适配和 worked / failed 反馈，而不是只展示一个高成功率数字。

### 4.9 Axiqra 不是只服务个人开发者的工具

个人开发者是重要用户，但 Axiqra 的完整形态必须同时服务：

1. 个人开发者。
2. 初级开发者和学习型用户。
3. 中高级工程师。
4. Tech Lead。
5. 小团队。
6. 企业研发团队。
7. 企业自研 Agent 团队。
8. 认证贡献者。
9. 审核者和维护者。
10. 外部 AI 编程工具。

### 4.10 Axiqra 不是只靠 MVP 后续补丁扩展的产品

Axiqra 的 MVP 必须在终局逻辑架构下最小启用。

这意味着第一版可以少实现能力，但不能缺少未来升级需要的核心边界，包括：

1. 空间。
2. 租户。
3. 权限。
4. 状态。
5. 可见性。
6. 来源。
7. 验证等级。
8. 索引生命周期。
9. 贡献账本。
10. 授权范围。
11. 数据导出和迁移。
12. 接入方式扩展。

## 5. 当前阶段边界

### 5.1 当前阶段的产品阶段

当前阶段可以定义为：

工程方案记忆层的完整原型与 MVP 启用阶段。

这个阶段有两个同时存在的目标：

1. 原型层面尽量完整展示产品形态，便于理解、传播、验证和反推数据模型。
2. 工程实现层面先启用最小闭环，避免过度实现导致验证变慢。

因此，当前阶段不是“只做一个很小的功能集合”，也不是“马上实现终局产品”。正确边界是：

完整产品形态先设计清楚；MVP 只启用当前闭环所需能力；数据模型、状态、空间、权限、接入和架构必须为后续演进预留。

### 5.2 当前阶段必须成立的核心闭环

当前阶段至少要让以下闭环在产品、原型和文档中成立。

| 闭环 | 当前阶段要求 |
|---|---|
| AI 调用闭环 | 外部 AI 工具能在任务前搜索 Solution 或 Public Case，并获得可执行参考 |
| 任务后回传闭环 | AI 工具能根据任务过程生成 Draft Case，用户确认后提交 |
| 人类学习闭环 | 开发者能阅读 Public Case，理解排查过程、失败路径和验证方式 |
| Solution 演进闭环 | Case、Invocation、worked / failed 反馈能推动 Solution 状态和内容演进 |
| 内容治理闭环 | 公开内容和高风险内容不能绕过授权、脱敏、审核和质量控制 |
| 贡献归因闭环 | 有效贡献、学习行为、调用反馈和未来权益资格能进入贡献账本 |
| 团队复用闭环 | 团队经验能够在团队空间中沉淀、复用和被内部 AI 调用 |

## 6. 长期阶段边界

Axiqra 的长期演进应分为产品形态演进和技术规模演进两条线。两条线有关联，但不能混为一谈。

### 6.1 产品形态演进

| 阶段 | 产品形态 | 核心目标 |

| P0 完整原型阶段 | 页面和交互尽量完整呈现 | 让用户、团队、投资人、开发者和 AI 都能理解产品全貌 |

### 6.2 技术规模演进

技术规模路线由 D10、D11、D12 详细展开。本文只定义上层边界。

## 8. 核心闭环

### 8.1 AI 工具调用闭环

AI 工具调用闭环描述外部 AI 编程工具如何使用 Axiqra。

基本过程：

1. 用户通过对话式自动接入、接入包 / Skill Pack、MCP、CLI、API 或插件让 AI 工具连接 Axiqra。
2. AI 工具在工程任务开始前，将任务目标、技术栈、环境、约束和风险要求发送给 Axiqra。
3. Axiqra 返回候选 Solution、关联 Public Case、适用边界、验证方式和风险提示。
4. AI 工具结合当前项目上下文执行工程任务。
5. Axiqra 不直接执行修复、测试或部署。
6. 任务结束后，AI 工具整理失败尝试、证据、修复步骤和验证结果。
7. 用户确认后生成 Draft Case 或提交 Case Package。
8. Axiqra 进入脱敏、结构化、审核、归档、关联和 Solution 演进流程。

详细流程进入 D05，接入协议进入 D09。

### 8.2 人类学习闭环

人类学习闭环描述开发者如何通过 Axiqra 学习真实工程过程。

基本过程：

1. 开发者搜索问题、技术栈、错误签名或场景。
2. Axiqra 返回 Public Case 和可读 Solution。
3. 开发者阅读问题现场、排查时间线、失败路径、证据链、根因、修复和验证方式。
4. 开发者收藏、学习、反馈、纠错或标记不适用。
5. 学习行为和反馈进入学习记录和贡献账本。
6. 高价值反馈影响内容质量、搜索排序和 Solution 演进。

详细学习体验进入 D05、D07、D17。

### 8.3 团队工程记忆闭环

团队工程记忆闭环描述团队如何把踩过的坑转为团队资产。

基本过程：

1. 团队成员接入 Axiqra。
2. 团队项目中的工程任务自动沉淀为 Project Case。
3. 团队管理员或负责人审核、归类、脱敏和维护团队 Case。
4. 团队内部形成 Team Solution、Prompt Pack、Rule Pack 或 Skill Pack。
5. 团队内部 AI 工具优先调用本团队工程记忆。
6. 团队可选择将部分内容脱敏后贡献为 Public Case 或公共 Solution 证据。
7. 团队保留导出、删除、授权撤销和审计权利。

详细空间、权限和企业能力进入 D13。

### 8.4 Solution 演进闭环

Solution 演进闭环描述方案如何从一次经验变成长期工程资产。

基本过程：

1. 一个或多个 Case 形成 Candidate Solution。
2. Candidate Solution 被 AI 工具或人类用户调用和查看。
3. Invocation 反馈记录 worked、failed、partial 或 not applicable。
4. 审核者、维护者或系统根据证据调整状态。
5. 多个相似 Case 可以融合为更稳定的 Solution。
6. 场景差异明显时可以分叉。
7. 技术过期、风险过高或证据不足时可以废弃、归档或隔离。
8. 搜索和推荐根据状态、验证等级、样本量、场景适配和可信来源调整排序。

状态机和验证等级进入 D08，搜索排序进入 D12。

### 8.5 贡献激励闭环

贡献激励闭环描述高质量贡献如何被记录和激励。

基本过程：

1. 用户阅读、反馈、纠错、提交 Case、维护 Solution 或提供验证证据。
2. 系统写入 Contribution Ledger。
3. 贡献根据质量、验证、授权、反作弊状态和实际复用价值计算资格。
4. 早期可体现为积分、认证、API 权益或 Pro 抵扣。
5. 长期商业化成熟后，可进入贡献者收益池候选。

详细激励机制进入 D15。

## 10. 设计原则

### 10.1 真实工程过程优先

Axiqra 优先沉淀真实工程过程，而不是泛泛的技术结论。

一个内容如果没有上下文、证据、失败路径、验证方式和适用边界，就不应被当作高可信工程记忆。

### 10.2 AI 用方案，人看过程

AI 工具需要可执行、可判断、可验证的 Solution。

人类开发者需要可学习、可复盘、可理解的 Public Case。

两条主线都必须存在。不能只做 AI 调用，也不能只做公开案例展示。

### 10.3 上下文和适用边界优先

Axiqra 不直接推荐“最先进技术”，而是沉淀“在特定产品阶段、团队规模、技术栈、风险约束和业务目标下适合的工程方案”。

任何 Solution 都必须说明：

1. 适用场景。
2. 不适用场景。
3. 前置条件。
4. 风险。
5. 验证方式。
6. 回滚或替代方案。

### 10.4 验证等级、样本量和风险等级分开

成功率不能脱离样本量、来源、审核、场景和调用方可信度。

Axiqra 的可信判断必须同时展示验证等级、样本量、证据质量、独立工程上下文、风险等级、适用边界、维护状态和真实调用反馈。

验证等级采用 L0-L5。L0 是未验证草稿；L1-L5 表达的是真实工程上下文中的验证充分度，不是绝对正确等级。一个 L5 Solution 也不能被理解为永远正确，只能表示它在记录的产品场景、工程约束、技术版本、验证样本和调用反馈下达到当前最高可信等级。

风险等级必须和验证等级分开。高风险或极高风险方案即使达到 L5，也不能让 AI 自动执行，只能作为高可信参考，并必须要求人工确认、领域审核或企业确认。

D08 必须完整承接用户提供的 L0-L5 分级、样本量展示、加权有效率、降级机制和风险等级规则。

### 10.5 失败路径必须沉淀

失败路径不是噪音，而是工程记忆的重要资产。

失败路径可以帮助 AI 和人类：

1. 避免重复尝试错误方向。
2. 判断方案不适用边界。
3. 识别根因和表象之间的差异。
4. 形成更稳定的 Solution。

### 10.6 用户确认优先

Axiqra 不能让 AI 自动公开内容、自动标记 Verified、自动执行高风险操作或自动上传敏感数据。

关键动作必须有用户、团队管理员、审核者或企业授权参与。

### 10.7 治理先于开放

Axiqra 不能先开放投稿，再事后治理。

公开内容、共享内容和可被 AI 高优先级调用的内容，必须先具备来源、授权、脱敏、审核、验证和污染隔离机制。

### 10.8 完整原型先行，MVP 最小启用

Axiqra 的原型应该尽量完整，因为原型最容易帮助用户理解、传播、讨论和反推数据模型。

但工程实现的 MVP 应最小启用，先跑通最关键闭环。完整原型和最小实现不是矛盾关系，而是两个层面的工作：

1. 原型负责展示完整产品形态。
2. MVP 负责验证最小可运行闭环。

### 10.9 终局逻辑架构先设计，物理部署分阶段

Axiqra 不能采用先随便做、后面推倒重构的方式。

第一版就必须预留：

1. 空间和租户。
2. 权限和可见性。
3. 状态机。
4. 来源和授权。
5. 索引生命周期。
6. 贡献账本。
7. 数据导出、删除和迁移。
8. 搜索引擎替换。
9. 向量引擎替换。
10. 模型网关和接入协议扩展。

### 10.10 数据隔离和联合检索解耦原则

个人、团队、企业和公共内容必须有清晰的可见性控制。

> [!IMPORTANT]
> **多空间联合检索与权重解耦规范：**
> * **上下文切换仅改变写入指向与搜索倾向**：当用户在顶部 navbar 切换“当前空间”上下文时，搜索引擎绝不物理隔离数据库。
> * **混合加权匹配机制 (Rank Boost)**：检索工作台及全局快速查找（Ctrl+K）将保持跨空间全可见度（可混合命中 Hobby、Team、Enterprise 和 Public 资产），但系统为“当前空间”上下文匹配出来的结果自动赋予 **`+25% matching ranks boost`** 的推荐排序权重。
> * **权限预过滤**：在向量及全文检索的 DB 检索阶段必须进行租户与权限预过滤（Pre-filtering），杜绝“先召回、后过滤”产生的内存泄露与安全越权隐患。企业空间内容默认不公开、不作为大模型训练数据，只有在显式授权、脱敏和审核后方可流转为公共注册表资产。

### 10.11 对话式自动接入优先

Axiqra 的快速接入不应只依赖命令行或手动配置。

优先接入体验应该是：

1. 用户复制一段接入指令给 AI 工具。
2. AI 工具读取接入描述、安装清单、接入包、Skill Pack 或等价文件。
3. AI 工具自动完成授权、配置、规则安装、MCP 配置、CLI 降级准备和环境检测。
4. AI 工具返回授权码、绑定状态、安装结果和诊断信息。
5. 用户在页面中确认绑定。

这里的“Skill”只能是接入包的一种可能形态，不能把快速接入窄化为单一 Skill。MCP、CLI、API、SDK 和插件是底层能力，不应压过对话式自动接入体验。

### 10.12 贡献归因和反作弊同时设计

Axiqra 需要鼓励高质量贡献，但不能奖励灌水、抄袭、刷 worked、重复提交或未授权导入。

贡献激励必须和 Contribution Ledger、授权范围、验证等级、反作弊状态和实际复用价值绑定。

### 10.13 可迁移、可导出、可删除

Axiqra 面向团队和企业时，数据必须可治理。

产品从第一阶段就应考虑：

1. 数据导出。
2. 历史导入。
3. 授权撤销。
4. 删除证明。
5. 空间迁移。
6. SaaS 到专属租户或私有化的迁移路线。

### 10.14 不用宣传承诺替代验证

Axiqra 的价值可以通过减少重复推理、减少重复排查、提升复用效率、帮助新人学习和沉淀团队资产体现。

但任何成本节省、ROI、商业价值、成功率、搜索质量和企业采用判断，都必须进入验证体系，不能只靠宣传话术。

## 11. 当前阶段优先级原则

当前阶段的优先级不是“功能越多越好”，而是“完整形态清楚、最小闭环可验证、后续扩展不变成补丁”。

### 11.1 必须优先保证的能力

### 14.1 D08 必须承接的验证等级规则摘要

本文档只固定验证等级的上层原则。完整规则进入 D08。

验证等级的基本原则：

1. Axiqra 不输出绝对标准答案。
2. 验证等级表达的是一个 Solution 在已知产品场景、工程约束、技术版本、验证证据和调用反馈下，被验证到什么程度。
3. L5 也不能被解释为永远正确，只能表示当前记录上下文中的最高可信等级。
4. 可信度不能只看成功率，必须同时看证据强度、样本数量、样本独立性、来源多样性、适用边界、失败处理、风险等级和持续维护。
5. 个人开发者、独立开发者、开源维护者、小团队、企业空间、官方种子和 Axiqra 自身 Dogfooding 都可以形成可信验证来源。
6. 可信度来自真实工程上下文、验证证据、调用反馈、适用边界、失败路径和长期稳定表现，不来自组织规模本身。

验证等级总览：

| 等级 | 名称 | 核心含义 | AI 调用建议 |
|---|---|---|---|
| L0 | 未验证 / 草稿级 | 没有真实工程验证，可能来自 AI 初稿、个人笔记、未确认回传或候选内容。 | 不建议 AI 自动调用，只能作为背景参考。 |
| L1 | 用户确认有效 | 至少 1 个真实 Project Case，用户确认 worked，有基本工程上下文，但缺少客观证据。 | 仅参考，执行前需要用户确认。 |
| L2 | 有客观证据验证 | 至少 1 个真实 Project Case、用户确认 worked，并有测试、CI、日志、部署、截图、PR / Issue、企业验证或类似客观证据。 | 可作为候选，低风险场景可提示性推荐。 |
| L3 | 可复现验证 / 多次有效 | 至少 2 个独立 Project Case 且每个达到 L2，或 1 个 L2 Case 加可复现环境并经可信审核。 | 可推荐，低风险场景可半自动执行，中高风险需要确认。 |
| L4 | 多上下文稳定验证 | 至少 5 次适用调用、3 个独立工程上下文、3 次 L2 以上证据型 worked、加权成功率不低于 80%，并有边界、失败路径、风险提示和可信维护。 | 可优先推荐，低风险可自动采用，中高风险需人工确认。 |
| L5 | 跨上下文长期稳定验证 | 至少 15 次适用调用、5 个独立工程上下文、2 类来源、8 次 L2 以上证据型 worked、加权成功率不低于 85%，并处于维护状态。 | 高可信优先，但高风险任务仍不能自动执行。 |

样本量展示规则：

> [!WARNING]
> **低置信度数据积累期规避法则 (Threshold Guard)：**
> 当方案关联的累计调用次数（total calls）少于 **5 次** 时，系统在 UI 界面上必须强制显示为 `数据积累中... (N/A)`，禁止输出任何百分比成功率，以防小样本数据产生过度自信或过快评级的系统偏差。

| 样本量 | 展示方式 |
|---|---|
| 适用调用少于 5 次 | 不显示成功率百分比，只显示样本数和验证说明（显示为 N/A 数据积累中）。 |
| 适用调用 5 到 14 次 | 可以显示成功率，但必须标记低样本。 |
| 适用调用不少于 15 次 | 可以显示成功率、样本量和可信区间或上下文说明。 |

加权有效率规则：

| 调用结果 | 权重或处理 |
|---|---|
| worked | 1.0 |
| partial | 0.5 |
| failed | 0 |
| not_applicable | 不计入成功率分母，但必须用于更新不适用边界、前置条件和匹配规则。 |

降级和复核规则必须覆盖：

1. 180 天无新验证，标记 Needs Review。
2. 365 天无新验证，自动降低 1 级或进入待复核状态。
3. 出现严重安全、数据或资损风险，立即进入 Quarantined。
4. 连续 3 次 failed，暂停推荐并进入复核。
5. failed 率超过 30%，降级并要求重新整理边界。
6. 大量 not_applicable，降低匹配权重并要求补充适用条件。
7. 核心依赖版本变化，标记 Version Review。

风险等级必须独立于验证等级：

| 风险等级 | 含义 | AI 调用约束 |
|---|---|---|
| R0 | 无风险，阅读、解释、文档类。 | L3 以上可推荐。 |
| R1 | 低风险，局部配置或容易回滚的低影响修改。 | L3 以上可推荐，低风险场景可半自动执行。 |
| R2 | 中风险，影响服务行为。 | L3 以上可推荐，但必须用户确认。 |
| R3 | 高风险，涉及生产、数据、安全、权限、支付、网关或核心链路。 | L4 以上才推荐，且必须人工确认或领域审核。 |
| R4 | 极高风险，可能造成数据丢失、资损、合规问题或大规模服务中断。 | L5 也不能自动执行，只能作为审查参考。 |

## 15. 当前结论

Axiqra 当前应被定义为工程方案记忆层，而不是普通知识库、提示词库、排障执行平台、技术论坛或新的 AI 编程工具。

它的第一阶段必须同时成立三件事：

1. AI 能调用 Solution。
2. 人能阅读 Public Case 学习真实工程过程。
3. 团队能把工程经验沉淀为可复用、可治理、可迁移的资产。

它的 MVP 不能只做一个小功能集合，而必须在完整产品形态和终局逻辑架构之下最小启用。原型应尽量完整，研发实现可以分期；公开内容可以存在，但必须授权、脱敏、审核和治理；企业和团队能力可以后置实现，但页面、对象和架构必须预留；贡献激励可以先记录账本和资格，不承诺现金比例；技术上可以用轻量栈验证，但不能把轻量栈写成终局规模化方案。
