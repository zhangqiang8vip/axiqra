# Axiqra 产品介绍与全流程总览

版本：v0.1
状态：Review
来源：基于 `axiqra 产品愿景文档.txt` 全文重构总结
用途：作为 Axiqra 对内统一认知、对外产品介绍、后续 PRD / Excel / 功能拆解的母文档

## 1. 一句话介绍

Axiqra 是 AI Agent 时代的工程方案记忆层。

它让 Cursor、Claude Code、Codex、OpenClaw、Gemini CLI、企业自研 Agent 等外部 AI 编程工具，在执行工程任务前先调用真实工程方案，在任务完成后自动回传工程过程，并通过 Case、Solution、Prompt、Rule、Skill、Invocation 和 worked / failed 反馈，让每一次真实工程活动沉淀为下一次 AI 可以复用、验证、融合和进化的工程记忆。

更直白地说：

```text
别让 AI 每次都从零生成同一类工程方案。
```

更完整地说：

```text
Axiqra 让每一次真实工程方案，都沉淀为下一次 AI 可以调用、验证、复用、融合和进化的工程记忆。
```

## 2. 为什么需要 Axiqra

AI 编程工具已经能写代码、改代码、解释报错、生成测试、设计架构、制定方案和协助部署。

但它们仍然缺少一件事：

```text
长期、可信、可调用、可反馈的工程记忆。
```

今天的软件工程里，大量真实经验会消失在：

1. 一次 AI 对话窗口里。
2. 一个临时终端会话里。
3. 一条群聊记录里。
4. 一次 PR 讨论里。
5. 一个本地 Markdown。
6. 一个没有人再打开的企业 Wiki。
7. 某个老员工的个人记忆里。

于是同样的问题、同样的方案、同样的技术取舍、同样的失败路径，会被不同开发者、不同团队、不同 AI 工具反复重新推理。

Axiqra 要解决的不是“让 AI 更会生成代码”，而是：

```text
让 AI 不再重复推理已经被真实验证过的工程方案。
```

## 3. Axiqra 的核心定位

Axiqra 不是以下产品：

| 不是 | 原因 |
|---|---|
| 不是普通知识库 | 知识库保存文档，Axiqra 保存带上下文、证据、失败路径和反馈的工程过程 |
| 不是技术论坛 | 论坛依赖开放讨论，Axiqra 依赖真实工程调用、验证和治理 |
| 不是提示词库 | Prompt 只是资产之一，必须绑定真实 Case、Solution 和调用反馈 |
| 不是排障网站 | 排障只是高频入口，Axiqra 覆盖所有工程方案 |
| 不是新的 AI 编程工具 | Axiqra 当前不替代 Cursor、Claude Code、Codex，而是增强它们 |
| 不是默认训练数据交易平台 | 数据训练、评测、商业授权必须由用户或企业明确授权 |

Axiqra 真正是：

```text
AI 可调用的工程方案记忆基础设施。
```

它沉淀的不是“最优技术”，而是：

```text
在什么产品阶段、团队规模、技术栈、业务约束、风险要求和验证证据下，什么工程方案更适合。
```

## 4. Axiqra 沉淀什么

Axiqra 不只沉淀 Bug 修复。

它沉淀所有真实工程方案，包括：

1. Bug 修复。
2. 故障排查。
3. 功能交付。
4. 技术选型。
5. 架构决策。
6. 性能优化。
7. 安全加固。
8. 数据库迁移。
9. CI/CD 和部署运维。
10. 测试方案。
11. 技术文档方案。
12. PRD、蓝图、架构说明书的形成过程。

每一次工程方案都应该尽量记录：

1. 工程目标。
2. 产品阶段。
3. 技术栈和版本。
4. 团队规模和维护能力。
5. 业务约束。
6. 成本和上线周期。
7. 候选方案。
8. 被放弃的方案。
9. 失败路径。
10. 最终选择。
11. 执行步骤。
12. 验证方式。
13. 风险和回滚。
14. 适用边界。
15. 不适用场景。
16. 后续调用反馈。

这就是 Axiqra 和普通知识库的区别：

```text
Axiqra 记录的是工程方案背后的判断条件。
```

### 4.1 工程方案适配关系

Axiqra 的核心对象不是“技术”，而是“工程方案适配关系”。

它不只是告诉 AI：

```text
应该用 PostgreSQL。
应该拆微服务。
应该加消息队列。
应该上缓存。
```

它更重要的是告诉 AI：

```text
在什么产品阶段、团队规模、业务复杂度、数据一致性要求、交付周期、成本约束和运维能力下，这个方案为什么适合，为什么不适合，什么时候需要升级。
```

因此，一个 Solution 不能只是技术答案，而必须绑定适配条件：

| 适配维度 | 说明 |
|---|---|
| 产品阶段 | MVP、增长期、平台化、大规模阶段 |
| 团队规模 | 个人、小团队、多团队、企业研发组织 |
| 业务复杂度 | 单一业务、跨域业务、强流程业务、交易链路 |
| 技术栈 | 框架、语言、中间件、数据库、部署环境 |
| 数据要求 | 一致性、事务、读写模式、数据量、迁移风险 |
| 稳定性要求 | 是否生产环境、是否高可用、是否可回滚 |
| 交付周期 | 快速试错、稳定交付、长期演进 |
| 运维能力 | 是否具备监控、告警、灰度、回滚、链路追踪 |
| 风险等级 | 是否涉及生产、权限、支付、安全、数据删除 |
| 升级条件 | 什么时候从当前方案迁移到更复杂方案 |

Axiqra 真正要形成的是一张工程方案适配网络。

这张网络能回答：

1. 类似产品阶段下，别人怎么选。
2. 类似团队规模下，哪种方案维护成本更低。
3. 类似业务复杂度下，直接上复杂架构是否过度设计。
4. 类似风险等级下，哪些方案必须人工确认。
5. 哪些方案早期有效，但规模化后必须升级。
6. 哪些方案看起来高级，但对小团队是负担。

这也是 Axiqra 区别于 Codemory 类“代码上下文记忆”或普通知识库的核心差异之一：

```text
Axiqra 不只是记住上下文，而是沉淀工程判断。
```

## 5. 核心资产：Project Case、Public Case、Solution

Axiqra 把一次真实工程过程拆成三种核心形态。

在 Project Case 形成前，AI 工具应先整理 Engineering Trace Package，也就是工程轨迹包。

工程轨迹包不是只记录“做了哪些步骤”，而是记录一次工程活动的完整轨迹：

1. 正向路径：目标、上下文、方案选择、执行步骤、修改内容、验证结果。
2. 反向路径：异常、失败、回归、根因、修复点、回滚过程。
3. 决策路径：为什么选这个方案，为什么不选另一个方案，适用边界是什么。
4. 证据路径：日志、diff、测试、截图、命令输出、用户确认。
5. 回滚路径：失败后如何恢复、撤销、降级或绕行。
6. 演化路径：这次经验如何进入 Project Case、Public Case、Solution 或 Candidate Seed。

Case Package 可以作为 Engineering Trace Package 的提交格式之一。Project Case 是它沉淀后的资产形态。

### 5.1 Project Case

Project Case 是原始、私有、完整的工程过程记录。

它保存：

1. 项目上下文。
2. 仓库或系统背景。
3. 原始日志摘要。
4. 配置片段。
5. AI 对话摘要。
6. 修改动作。
7. 验证结果。
8. 附件和证据引用。

Project Case 默认属于个人、团队或企业空间，不直接公开。

它的价值是：

```text
完整、真实、可追溯。
```

### 5.2 Public Case

Public Case 是从 Project Case 脱敏、清洗、抽象出来的公开学习版本。

它去掉：

1. 项目名。
2. 仓库地址。
3. 真实路径。
4. Token、密码、密钥。
5. 内网 IP。
6. 客户名。
7. 私有业务数据。

它保留：

1. 工程目标。
2. 技术栈。
3. 问题现场。
4. 排查时间线。
5. 失败假设。
6. 取舍理由。
7. 根因判断。
8. 修复步骤。
9. 验证方式。
10. 学习总结。

Public Case 面向人类开发者，尤其是新人和学习型开发者。

它的价值是：

```text
让人看到真实工程思维，而不是只看到最终答案。
```

### 5.3 Solution

Solution 是从一个或多个 Case 中聚合出来的标准工程方案。

它面向 AI 工具和开发者复用。

一个 Solution 应包含：

1. 解决什么问题。
2. 适合什么产品阶段。
3. 适合什么技术栈。
4. 适合什么团队规模。
5. 需要什么前置条件。
6. 不适合什么场景。
7. 执行步骤。
8. 验证步骤。
9. 风险提示。
10. 回滚建议。
11. 失败路径。
12. 常见 AI 误判。
13. 推荐 Prompt。
14. 推荐 Rule。
15. 推荐 Skill。
16. 关联 Case。
17. worked / failed / partial / not_applicable 反馈。
18. 验证等级和风险等级。

Solution 的价值是：

```text
给 AI 调用，给人复用，给团队沉淀。
```

## 6. 产品核心飞轮

Axiqra 的核心不是保存内容，而是让工程方案在真实调用中持续进化。

完整飞轮如下：

```text
外部 AI 工具接入 Axiqra
-> AI 执行工程任务前搜索 Axiqra
-> Axiqra 返回候选 Solution、Public Case、失败路径和风险提示
-> AI 判断方案是否适配当前项目
-> AI 执行工程任务
-> AI 整理 Engineering Trace Package，记录正向、反向、决策、证据、回滚和演化路径
-> 用户确认、编辑或拒绝
-> 以 Case Package 形式回传 Axiqra
-> Axiqra 生成 Project Case
-> 用户选择私有保存、脱敏公开或参与 Solution 融合
-> 平台 AI 初审
-> 必要时认证开发者 / 审核者二审或多轮审查
-> 形成 Public Case 或 Candidate Solution
-> 多个 Case 融合为 Solution
-> Solution 被下一次 AI 调用
-> worked / failed / partial / not_applicable 反馈继续更新 Solution
```

这条飞轮可以归纳为：

```text
调用 -> 执行 -> 回传 -> 审查 -> 融合 -> 升级 -> 再调用
```

### 6.1 无命中、覆盖范围与 Candidate Seed

Axiqra 不能为了显得“什么都知道”而在无命中时乱推荐。

当搜索没有找到足够适配的 Solution 或 Public Case 时，正确流程不是返回泛化答案，而是进入覆盖范围和候选种子路径。

标准流程：

```text
用户或 AI 发起搜索
-> Axiqra 判断当前技术栈、错误签名、产品阶段或任务类型覆盖不足
-> 页面或 API 返回无命中 / 低覆盖说明
-> 引导进入 Candidate Seed
-> 用户、AI、维护者或认证者提交候选问题、工程目标、上下文、失败路径和验证证据
-> 平台记录为低可信候选种子
-> 达到基础质量门槛后进入 Candidate Pool
-> 由大众继续补充，或由维护者、认证开发者和认证审核者认领协作
-> 形成 Candidate Case 或 Candidate Solution
```

Candidate Seed 的价值是：

1. 防止 Axiqra 用不相关内容填充搜索结果。
2. 告诉用户当前哪些领域覆盖不足。
3. 把无结果转化为内容冷启动任务。
4. 让大众可以低门槛创建真实需求，但通过质量门槛控制可信资产。
5. 让维护者和认证开发者知道下一批应该补什么。
6. 让平台可以统计真实需求，而不是凭空规划内容。

覆盖范围应至少能说明：

| 覆盖维度 | 说明 |
|---|---|
| 技术栈覆盖 | Redis、Docker、Spring Boot、PostgreSQL、Kubernetes 等 |
| 场景覆盖 | 排障、功能交付、架构、性能、安全、文档方案等 |
| 验证等级覆盖 | L0-L5 分布 |
| 风险等级覆盖 | R0-R4 分布 |
| 最近验证时间 | 是否长期未维护 |
| 空间覆盖 | 公共、个人、团队、企业空间 |

因此，Axiqra 的可信表达不是“我们什么都有”，而是：

```text
有覆盖就给可信方案，没有覆盖就诚实进入候选种子。
```

## 7. 用户怎么用

### 7.1 个人开发者

个人开发者的典型使用路径：

```text
进入 Axiqra
-> 搜索工程问题或方案
-> 阅读 Public Case 或 Solution
-> 接入自己的 AI 编程工具
-> 让 AI 工具任务前先查 Axiqra
-> 任务完成后自动整理 Engineering Trace Package
-> 用户确认后回传 Case Package
-> 保存为个人 Project Case
-> 选择是否脱敏公开或参与 Solution 融合
```

个人开发者获得的价值：

1. 少重复排查。
2. 少被 AI 带错方向。
3. 学习真实工程过程。
4. 保存自己的工程记忆。
5. 贡献高质量 Case 后获得积分、认证和未来权益资格。

### 7.2 AI 工具重度用户

AI 工具用户的典型使用路径：

```text
复制 Axiqra Connect 指令给 AI 工具
-> AI 工具自动读取接入说明
-> 完成授权、配置、doctor 自检
-> 工程任务前自动搜索 Axiqra
-> 执行时引用 Solution
-> 完成后生成 Engineering Trace Package
-> 用户确认后回传
```

它的价值是：

```text
让现有 AI 工具拥有工程方案记忆。
```

### 7.3 团队 Owner / Tech Lead

团队的典型使用路径：

```text
创建团队空间
-> 接入团队项目和 AI 工具
-> 团队工程任务自动沉淀为 Project Case
-> Owner Review 复核关键 Case
-> 形成团队内部 Solution
-> 新人和团队 AI 工具优先调用团队记忆
-> 部分内容脱敏后贡献到公共空间
```

团队获得的价值：

1. 团队踩过的坑不再散落。
2. 新人能学习真实案例。
3. 内部 AI 能调用团队经验。
4. 老员工经验变成团队资产。
5. 团队 Solution 可以持续维护和升级。

### 7.4 企业

企业的典型使用路径：

```text
创建企业空间
-> 配置租户、成员、权限、SSO / SCIM
-> 接入企业自研 Agent 或内部 AI 工具
-> 企业工程过程默认私有保存
-> 企业内部形成 Project Case、Public Case、Solution、Prompt、Rule、Skill
-> 企业 Agent 优先调用企业内部工程记忆
-> 企业可选择只内部使用、匿名统计、脱敏贡献或授权评测
```

企业获得的价值：

1. 企业内部工程经验可被 Agent 调用。
2. 不需要一开始训练大模型，也能形成企业智能体记忆。
3. 私有 SDK、内部框架、历史架构和部署经验可以沉淀。
4. 企业数据默认不公开、不训练、不进入公共收益池。
5. 可以审计、导出、删除、撤回授权。

### 7.5 贡献者和认证开发者

贡献者的典型路径：

```text
提交真实 Case 或反馈
-> 平台记录贡献账本
-> Case 被审核、调用、融合
-> worked 反馈提升贡献价值
-> 贡献者获得积分、认证、权益
-> 高质量贡献者可成为认证开发者、认证审核者或 Solution Maintainer
```

贡献者生态的原则：

```text
不奖励灌水，奖励真实工程价值。
```

## 8. 接入流程

Axiqra Connect 是用户进入产品的关键入口。

目标不是让用户手动研究复杂配置，而是：

```text
一句话让现有 AI 工具接入 Axiqra。
```

标准流程：

1. 用户进入接入页。
2. 选择目标工具，例如 Codex、Claude Code、Cursor、通用 MCP 客户端或企业 Agent。
3. Axiqra 生成可复制给 AI 工具的接入指令。
4. AI 工具读取接入包或 manifest。
5. AI 工具完成 MCP、CLI、API Key、Rules、Skill Pack 等配置。
6. 用户完成授权或回填授权码。
7. doctor 检测网络、鉴权、权限、版本、搜索、回传能力。
8. 接入成功后执行一次测试搜索。
9. 平台记录接入会话和状态。
10. 如果失败，降级到 CLI / REST API / 手动配置。

接入方式包括：

| 接入方式 | 作用 |
|---|---|
| 对话式接入 | 用户复制指令给 AI 工具，由 AI 工具自动完成 |
| 接入包 | manifest、配置、规则、权限、回退路径 |
| MCP | 支持 AI 工具调用 Axiqra 能力 |
| CLI | 本地初始化、搜索、回传、doctor |
| REST API | 企业 Agent、自研工具、平台级接入 |
| SDK | 后续深度集成 |
| Rule / Skill Pack | 指导 AI 工具如何搜索、调用和回传 |

## 9. 审查与治理流程

Axiqra 中的内容可能被 AI 用于真实工程任务，所以不能按普通社区内容处理。

完整审查流程如下：

```text
Engineering Trace Package / Case Package / Public Case / Candidate Solution 提交
-> 平台 AI 初审
-> 平台规则审查
-> 极低风险内容自动通过、自动拒绝或要求补充
-> 低风险内容进入候选池或抽检复核
-> 中高风险内容进入认证开发者审查
-> 高风险领域进入领域审核者多轮审查
-> 争议内容进入仲裁或申诉
-> 通过后发布、进入 Candidate / Reviewed / Verified
-> 上线后继续根据 worked / failed 反馈复核
```

### 9.1 平台 AI 初审

平台 AI 初审负责快速检查：

1. 结构是否完整。
2. 是否包含工程目标。
3. 是否包含技术栈和上下文。
4. 是否包含验证证据。
5. 是否缺少适用边界。
6. 是否过度泛化。
7. 是否疑似 AI 幻觉。
8. 是否包含危险命令。
9. 是否泄露敏感信息。
10. 是否与已有内容重复。

AI 初审可以处理极低风险内容的自动通过、自动拒绝或要求补充，但不能替代高风险人工审查。

### 9.2 平台规则审查

平台规则审查负责检查：

1. 可见范围。
2. 授权范围。
3. 是否允许公开。
4. 是否允许参与 Solution 融合。
5. 是否允许用于评测。
6. 是否允许训练。
7. 是否允许商业授权。
8. 是否符合企业私有边界。

### 9.3 认证开发者审查

普通内容可以通过平台 AI 初审和基础人工复审进入 Candidate 或 Reviewed。

但以下内容需要认证开发者或认证审核者参与：

1. 数据库迁移。
2. 生产部署。
3. 安全配置。
4. 权限治理。
5. 支付链路。
6. 网关流量切换。
7. 高可用架构。
8. 核心业务状态变更。
9. 数据删除和数据修复。

认证角色包括：

1. 认证后端工程师。
2. 认证前端工程师。
3. 认证数据库工程师。
4. 认证 DevOps 工程师。
5. 认证安全工程师。
6. 认证架构师。
7. 认证测试工程师。
8. 认证文档方案审查员。
9. Prompt / Rule / Skill Curator。
10. Solution Maintainer。

### 9.4 多轮审查与仲裁

高风险或争议内容可能需要：

1. 一审：平台 AI 初审。
2. 二审：认证开发者复审。
3. 三审：领域审核者交叉审核。
4. 平台终审：公开高风险 Solution 最终确认。
5. 申诉：贡献者或用户对拒绝、降级、隔离提出申诉。
6. 仲裁：平台、认证专家、企业管理员共同处理争议。

审查不是一次性动作。

上线后的 failed、partial、not_applicable 反馈也会触发复核、降级、隔离或分叉。

### 9.5 认证身份和审查权重

Axiqra 的认证开发者、认证审核者和 Solution Maintainer 不是一次性永久身份。

认证身份必须动态变化。

认证身份还应预留可验证能力档案和认证凭证能力，用于页面展示、审核权限、权重计算、有效期管理、撤销状态和公开验证。对外叙事可以保持克制，产品和数据结构需要知道它存在。

一个认证者的权重应受到以下因素影响：

| 影响因素 | 权重变化 |
|---|---|
| 审核内容后续多次 worked | 审核权重上升 |
| 审核内容后续多次 failed | 审核权重下降 |
| 放过危险方案 | 暂停或撤销审核权限 |
| 提交高质量失败路径 | 贡献权重上升 |
| 修正 Solution 边界 | 维护权重上升 |
| 灌水审核或低质贡献 | 降权、限流或撤销认证 |
| 领域贡献长期稳定 | 可升级为领域审核者或 Maintainer |

认证只能提高初始可信度和审核权重，不能直接替代验证。

最高可信仍然必须来自：

1. 真实工程上下文。
2. 验证证据。
3. 多次 Invocation。
4. worked / failed / partial / not_applicable 反馈。
5. 长期维护表现。

也就是说：

```text
认证是可信信号，不是最终真理。
```

## 10. 验证等级和风险等级

Axiqra 不承诺绝对正确。

它用验证等级表达“一个方案在已知上下文中被验证到什么程度”。

| 等级 | 含义 |
|---|---|
| L0 | 草稿或未验证 |
| L1 | 用户确认有效，但证据不足 |
| L2 | 有日志、命令、截图、测试等客观证据 |
| L3 | 可复现或多次有效 |
| L4 | 多上下文稳定验证 |
| L5 | 跨上下文长期稳定验证 |

风险等级独立于验证等级：

| 等级 | 含义 |
|---|---|
| R0 | 无风险，阅读、解释、文档类 |
| R1 | 低风险，局部配置或容易回滚 |
| R2 | 中风险，影响服务行为，需要确认 |
| R3 | 高风险，涉及生产、数据、安全、权限、支付等 |
| R4 | 极高风险，可能造成数据丢失、资损或大规模中断 |

原则：

1. L5 也不等于永远正确。
2. R3/R4 即使 L5，也不能自动执行。
3. 成功率必须结合样本量。
4. total < 5 时不能显示夸张成功率百分比。
5. failed、partial、not_applicable 都会影响边界和推荐。

### 10.1 空间、可信等级与授权边界

Axiqra 必须明确区分三件事：

```text
可见范围 != 可信等级 != 授权范围
```

一个内容公开，不代表它高可信。

一个内容在企业空间内私有，也不代表它低可信。

一个 Solution 被验证有效，也不代表它可以公开、训练、商业使用或进入收益池。

三套边界分别回答不同问题：

| 边界 | 回答的问题 | 示例 |
|---|---|---|
| 可见范围 | 谁能看 | 个人、团队、企业、公共空间 |
| 可信等级 | 这个方案有多可靠 | L0-L5、样本量、证据、反馈 |
| 授权范围 | 这个内容能被怎么使用 | 是否公开、是否训练、是否评测、是否商业授权、是否参与收益 |

因此，每个 Case / Solution / Prompt / Rule / Skill 都应记录授权和可见边界。

关键授权字段包括：

| 字段 | 含义 |
|---|---|
| `visibility_scope` | 谁可见 |
| `license_scope` | 授权范围 |
| `public_allowed` | 是否允许公开 |
| `solution_merge_allowed` | 是否允许参与 Solution 融合 |
| `eval_allowed` | 是否允许进入评测集 |
| `training_allowed` | 是否允许用于训练 |
| `commercial_allowed` | 是否允许商业授权 |
| `reward_eligible` | 是否具备收益池资格 |
| `redaction_status` | 脱敏状态 |
| `authorization_type` | 授权类型 |

默认策略必须保守：

1. 个人和企业私有内容默认不公开。
2. 默认不训练。
3. 默认不商业使用。
4. 默认不进入公共 Solution。
5. 默认不进入收益池。
6. 所有授权必须可追踪、可撤回、可审计。

这条原则对企业空间尤其重要：

```text
企业内容可以是高可信，但不一定公开。
公共内容可以被所有人看到，但不一定高可信。
```

## 11. 内容来源和冷启动

Axiqra 第一阶段不应该完全开放投稿。

它应该采用：

```text
受控种子 + 自动回传 + 分层验证
```

第一阶段内容来源包括：

| 来源 | 说明 |
|---|---|
| 官方种子 | 平台团队、核心开发者、可信专家整理的高质量样本 |
| Dogfooding | Axiqra 开发自身产生的工程 Case |
| 早期可信开发者 | AI 重度用户、中高级工程师、Tech Lead、独立开发者 |
| 企业私有数据 | 企业内部真实工程过程，默认私有 |
| 受控社区贡献 | 普通用户可贡献，但默认低可信，不污染核心库 |

第一阶段不应宣传“高成功率”，而应承诺：

```text
可验证、可追踪、可进化。
```

### 11.1 成功率来自 Invocation

Axiqra 不能允许用户自己填写成功率。

成功率也不能由点赞数、收藏数或评论热度决定。

Axiqra 的成功率必须来自真实 Invocation。

一次 Invocation 至少代表：

1. 某个 AI 工具、用户或系统调用了某个 Solution。
2. 调用发生在某个真实任务上下文中。
3. 调用后产生了结果。
4. 用户、系统或证据链返回 worked / failed / partial / not_applicable。
5. 平台记录了本次调用的上下文、来源、验证证据和反馈。

统计必须至少区分两类：

| 指标类型 | 内容 |
|---|---|
| 原始统计 | total、worked、failed、partial、not_applicable |
| 可信统计 | 可信调用次数、加权成功率、样本量等级、证据强度、来源权重 |

早期样本少时，不应该显示：

```text
成功率 100%
```

而应该显示：

```text
样本不足
数据积累中
仅 2 次验证
低样本可信度
不建议自动执行
```

这条规则是 Axiqra 建立信任的关键。

## 12. 团队与企业体系

### 12.1 团队空间

团队空间用于让团队工程经验被成员和 AI 复用。

核心能力：

1. 团队项目。
2. 团队 Project Case。
3. 团队内部 Solution。
4. Owner Review。
5. 团队学习复盘。
6. 团队调用统计。
7. 团队贡献账本。
8. 团队权限和成员管理。

团队空间的目标：

```text
让团队踩过的坑，成为团队成员和 AI Agent 可调用的工程记忆。
```

团队搜索和推荐应优先返回用户当前位置附近的记忆：

```text
当前项目 -> 小组 / Squad -> 团队 -> 企业 / 组织 -> 已授权公共内容 -> 普通公共内容
```

先权限过滤，再按空间距离、适配度、可信等级和最近验证时间排序。

### 12.2 企业空间

企业空间用于形成企业私有工程记忆。

核心能力：

1. 企业租户。
2. RBAC 权限。
3. 审计日志。
4. SSO / SCIM。
5. 企业内部 Project Case。
6. 企业内部 Solution。
7. 企业 Prompt / Rule / Skill。
8. 企业自研 Agent 接入。
9. 导入导出。
10. 删除和授权撤回。
11. 私有化部署路线。

企业空间原则：

```text
企业数据默认不公开、不训练、不进入公共收益池。
```

企业可以选择：

1. 仅内部使用。
2. 在小组、团队或企业范围内共享。
3. 只贡献匿名统计。
4. 脱敏后生成 Public Case。
5. 贡献通用 Solution 片段。
6. 贡献失败路径。
7. 授权进入评测集。
8. 授权训练或商业使用。

## 13. 贡献者和认证体系

Axiqra 的长期价值来自真实工程方案，而真实工程方案来自开发者、团队和企业。

贡献不应按数量奖励，而应按真实工程价值奖励。

贡献价值来自：

1. 是否来自真实工程过程。
2. 是否有验证证据。
3. 是否明确适用边界。
4. 是否补充失败路径。
5. 是否被 Solution 采用。
6. 是否被 AI 工具调用。
7. 调用后 worked 多少次。
8. failed 后是否修正边界。
9. 是否被企业采用。
10. 是否帮助工程轨迹、Solution、Prompt / Rule / Skill 进化。

贡献者成长路径：

```text
普通用户
-> 贡献者
-> 认证贡献者
-> 认证开发者
-> 认证审核者
-> 领域审核者
-> Solution Maintainer
```

激励形态：

1. 学习积分。
2. 贡献积分。
3. 认证身份。
4. API 权益。
5. Pro 抵扣。
6. 试点资格。
7. 未来收益池资格。

原则：

```text
不奖励灌水，不奖励抄袭，不奖励刷 worked，不奖励未授权内容。
```

## 14. 商业化、生态与绿色工程飞轮

Axiqra 的商业价值不是单一功能带来的，而是工程方案资产长期复利带来的。

它可以同时服务：

1. 个人开发者。
2. 中高级工程师。
3. Tech Lead。
4. 小团队。
5. 企业研发团队。
6. 企业自研 Agent 团队。
7. AI 编程工具厂商。
8. 模型厂商。
9. 云厂商。
10. DevOps / AI 开发平台。

商业化方向包括：

| 方向 | 说明 |
|---|---|
| 个人 Pro | 更大私有空间、高级搜索、更多接入额度 |
| API 调用额度 | AI 工具、企业 Agent、自研平台调用 |
| 团队空间 | 团队 Project Case、内部 Solution、Owner Review |
| 企业空间 | 租户、RBAC、审计、SSO / SCIM、私有 Agent |
| 私有化部署 | 专属租户、私有部署、混合部署 |
| 高级脱敏 | 企业级脱敏、授权、删除和审计 |
| Agent Eval | 授权工程方案数据形成评测集 |
| 数据授权 | 明确授权后的评测、训练或商业使用 |
| 工具生态合作 | 与 AI 编程工具、云厂商、DevOps 平台集成 |
| 贡献者权益 | 积分、认证、API 权益、Pro 抵扣、收益池资格 |

Axiqra 还具备绿色工程智能飞轮：

```text
真实工程方案进入 Axiqra
-> AI 工具优先复用历史 Solution
-> 重复推理减少
-> 错误尝试减少
-> Token、算力和人类等待时间下降
-> worked / failed 反馈继续更新 Solution
-> 下一次方案更准
-> 平台价值增强
-> 更多真实工程方案进入平台
```

这不是单纯节省 Token。

真正节省的是：

1. 重复上下文输入。
2. 重复方案生成。
3. 重复错误尝试。
4. 重复验证成本。
5. 重复架构讨论。
6. 重复部署排查。
7. 重复文档组织。
8. 开发者等待时间。
9. 团队沟通成本。

因此，Axiqra 的长期价值可以表达为：

```text
减少软件工程世界的重复方案生成和重复试错。
```

## 15. Axiqra 的完整产品主线

基于愿景文档，Axiqra 可以被总结为 20 条产品主线：

| 编号 | 产品主线 | 说明 |
|---:|---|---|
| 1 | 产品定位线 | AI Agent 时代的工程方案记忆层 |
| 2 | 用户角色线 | 个人、AI 工具用户、团队、企业、贡献者、审核者 |
| 3 | 工程方案适配线 | 不记录最优技术，而记录方案与场景的适配关系 |
| 4 | AI 接入线 | Axiqra Connect、MCP、CLI、API、SDK、Rules、Skills |
| 5 | 任务前调用线 | AI 执行前搜索 Solution、Public Case、团队 / 企业记忆 |
| 6 | 工程执行线 | AI 执行，人确认，Axiqra 不直接替代执行工具 |
| 7 | 自动回传线 | AI 生成 Engineering Trace Package，以 Case Package 形式确认并回传 |
| 8 | Project Case 线 | 原始私有工程过程保存 |
| 9 | Public Case 线 | 脱敏公开学习案例 |
| 10 | Solution 资产线 | AI 可调用、可反馈、可融合的标准方案 |
| 11 | Prompt / Rule / Skill 线 | 从真实工程反馈中进化的 AI 执行资产 |
| 12 | 搜索推荐线 | 多路召回、权限预过滤、排序、评测 |
| 13 | 覆盖范围与 Candidate Seed 线 | 低覆盖提示、无命中候选、大众创建、质量门槛、维护者和认证者协作 |
| 14 | 验证反馈线 | Invocation、worked、failed、partial、not_applicable、L0-L5、R0-R4 |
| 15 | 授权与可信边界线 | 可见范围、可信等级、授权范围三者分离 |
| 16 | 审查治理线 | 平台 AI 初审、风险分层自动 / 人工审核、认证开发者、多轮审查、仲裁 |
| 17 | 认证身份线 | 认证开发者、认证审核者、领域审核者、Solution Maintainer、能力档案和动态权重 |
| 18 | 团队企业线 | 团队空间、企业空间、私有 Agent、权限、审计、空间优先级搜索 |
| 19 | 贡献生态线 | 贡献账本、认证、积分、权益、收益池资格、反作弊 |
| 20 | 商业生态线 | Pro、API、企业试点、私有化、Agent Eval、数据授权、工具生态 |

这 20 条线是产品介绍层面的主线。

后续拆需求和 Excel 时，可以再按这些产品主线继续展开为一级功能域、二级路线、功能点、页面、API、数据对象、权限、状态和测试观点。

## 16. 最终总结

Axiqra 要做的不是一个更漂亮的知识库，也不是一个更热闹的开发者社区，更不是一个提示词模板网站。

Axiqra 要补上的是 AI Agent 时代软件工程缺失的一层基础设施：

```text
工程方案记忆层。
```

它让 AI 在做工程任务前先调用真实工程记忆。

它让 AI 完成任务后自动回传真实工程过程。

它让 Project Case 保存原始过程。

它让 Public Case 帮助人类学习。

它让 Solution 被 AI 调用、反馈、融合、升级。

它让失败路径、误判记录和不适用边界成为核心资产。

它让团队踩过的坑变成组织记忆。

它让企业不训练大模型也能拥有自己的智能体工程记忆。

它让贡献者的真实工程经验被记录、归因、审查和激励。

一句话：

```text
Axiqra 让软件工程从“经验散落时代”，进入“工程方案记忆时代”。
```
