# Axiqra 开发任务拆解、验收标准、风险与文档维护机制

版本：重构版 v0.2  
状态：Draft  
所属体系：D18 / 18

## 1. 文档定位

本文档定义开发任务拆解、验收标准写法、风险管理、ADR、RACI 和文档维护机制。

## 2. 日本式详细开发规格模板

每个功能必须按以下字段拆解：

| 字段 | 说明 |
|---|---|
| 功能编号 | 如 FEAT-SEARCH-001 |
| 功能名称 | 中文名称 |
| 功能目的 | 为什么做 |
| 使用角色 | 谁使用 |
| 触发入口 | 从哪个页面或 API 触发 |
| 前置条件 | 登录、权限、数据状态 |
| 输入内容 | 用户或系统输入 |
| 输入校验 | 必填、格式、边界 |
| 正常流程 | 主流程 |
| 异常流程 | 失败、无权限、网络错误 |
| 权限控制 | 谁能看、谁能改 |
| 数据保存 | 保存对象和字段 |
| 状态变化 | 状态迁移 |
| API 需求 | 方法、路径、参数 |
| 前端显示 | 页面、状态、错误提示 |
| 后端处理 | 服务逻辑 |
| 日志 / 审计 | 记录要求 |
| 验收标准 | Given / When / Then |
| 测试用例 | 正常、异常、权限、边界 |
| 优先级 | P0-P3 |
| 版本阶段 | P0 / S1 / S2 / S3 / S4 |

## 3. 验收标准写法

```text
给定：用户已登录并拥有目标对象读取权限。
当：用户点击“提交工程轨迹”。
则：系统必须校验必填路径、授权、证据和敏感信息；校验通过后生成 Project Case；校验失败时显示缺失项，不得创建不完整数据。
```

## 4. 开发任务分层

```mermaid
flowchart LR
    EPIC["Epic"] --> FEATURE["Feature"]

    TASK --> SUB["Sub Task"]

```

## 5. 风险台账

| 风险 | 影响 | 处理 |
|---|---|---|
| 产品跑偏成知识库 | 核心价值丢失 | D02/D05/D08 校验 |
| 私有数据泄露 | 企业不可用 | D13/D14 强约束 |
| 低质开放投稿污染 | 搜索可信度下降 | Candidate Seed 质量门槛 |
| AI 自动高风险执行 | 安全事故 | 高风险必须确认 |
| Excel 与文档不一致 | 排期错误 | 以 D01-D18 为准并追溯编号 |

## 6. 文档维护规则

| 规则 | 说明 |
|---|---|
| 单一主版本 | 每个 D 编号只保留一个主文件 |
| 状态明确 | Draft / Review / Accepted / Deprecated |
| 冲突登记 | 不直接覆盖冲突 |
| 追溯编号 | 功能、验收、测试、API 都可追溯 |
| 修改记录 | 重大变更写 ADR |

## 7. 验收标准

| 编号 | 验收内容 |
|---|---|
| AC-D18-001 | 功能拆解模板字段完整 |
| AC-D18-002 | 验收标准采用 Given / When / Then |
| AC-D18-003 | 风险台账有处理建议 |
| AC-D18-004 | Excel 能追溯功能、验收、测试 |
| AC-D18-005 | 文档状态和版本可维护 |

## 8. 编号体系

所有开发对象必须有稳定编号，便于 Excel、原型、接口、测试和文档互相追溯。

| 编号前缀 | 对象 | 示例 |
|---|---|---|
| DOC | 文档 | DOC-D09 |
| EPIC | 大功能域 | EPIC-SEARCH |
| FEAT | 功能点 | FEAT-SEARCH-001 |
| STORY | 用户故事 | STORY-SEARCH-001-01 |
| TASK | 开发任务 | TASK-SEARCH-001-01-BE |
| AC | 验收标准 | AC-SEARCH-001-01 |
| TC | 测试用例 | TC-SEARCH-001-01 |
| API | 接口 | API-SEARCH-001 |
| OBJ | 数据对象 | OBJ-007 |
| FIELD | 字段 | FIELD-SOLUTION-STATUS |
| PERM | 权限 | PERM-SOLUTION-READ |
| RISK | 风险 | RISK-GOV-001 |

编号规则：

1. 编号一旦进入开发，不随标题改名而变化。
2. 废弃编号不能复用。
3. Excel 中每行必须至少绑定一个 DOC 和一个 FEAT。
4. API、对象、权限、验收、测试必须能追溯到 FEAT。

## 9. 功能点颗粒度标准

功能点太粗会无法开发，太细会淹没管理。Axiqra 的功能点建议按“一个用户目标 + 一个系统结果 + 可验收边界”拆。

| 颗粒度 | 太粗示例 | 合格示例 | 太细示例 |
|---|---|---|---|
| 功能 | AI 工具接入 | 创建接入会话并生成接入指令 | 按钮颜色改成蓝色 |
| 功能 | 搜索系统 | Search Before Act 权限预过滤 | SQL 增加一个 where |
| 功能 | 审核系统 | R0 内容 AI 初审自动通过 | 显示一个标签 |
| 功能 | 权限系统 | 用户撤回 Public Case 授权 | 修改枚举文案 |

一个合格功能点必须回答：

1. 谁使用。
2. 从哪里进入。
3. 输入什么。
4. 系统保存什么。
5. 状态怎么变。
6. 权限怎么判断。
7. 错误怎么提示。
8. 怎么验收。
9. 怎么测试。

## 10. 详细开发规格模板

每个 P0/P1 功能都要写成下面的开发规格。Excel 可拆成多列，文档可保留成段落。

| 区块 | 必填 | 内容 |
|---|---|---|
| 基本信息 | 是 | 编号、名称、版本、优先级、负责角色 |
| 背景目标 | 是 | 为什么做，不做会怎样 |
| 用户角色 | 是 | 用户、AI Tool、审核者、企业管理员等 |
| 前置条件 | 是 | 登录、权限、对象状态、接入状态 |
| 入口 | 是 | 页面、按钮、API、MCP、CLI |
| 主流程 | 是 | 1-N 步 |
| 分支流程 | 是 | 不同角色、不同状态、不同风险 |
| 异常流程 | 是 | 无权限、缺字段、网络失败、重复提交 |
| 数据对象 | 是 | 新增、读取、修改的对象和字段 |
| 状态迁移 | 是 | 从什么状态到什么状态，由什么事件触发 |
| 权限规则 | 是 | RBAC、ABAC、授权范围 |
| API / MCP | 条件必填 | 请求、响应、错误码、幂等 |
| 前端交互 | 条件必填 | 页面状态、加载、空状态、错误提示 |
| 审计日志 | 是 | actor、action、target、result |
| 验收标准 | 是 | Given / When / Then |
| 测试用例 | 是 | 正常、异常、权限、边界、回归 |
| 风险 | 是 | 产品、技术、数据、安全、治理风险 |
| 上线影响 | 是 | 是否需要迁移、开关、灰度、回滚 |

## 11. Excel 扩展规则

Excel 不只是任务列表，而是开发控制台。

| 工作表 | 必须增加的字段 |
|---|---|
| 产品功能总表 | 一级类目、二级路线、三级功能、阶段、业务价值、依赖 |
| 详细开发任务表 | 前端、后端、数据、API、权限、审计、测试、负责人、状态 |
| 验收标准表 | Given、When、Then、验收证据、验收人 |
| 测试用例表 | 测试类型、前置数据、步骤、预期、自动化状态 |
| 页面交互验收 | 页面编号、控件编号、状态、错误提示、权限显示 |
| 数据对象字段 | 对象、字段、类型、枚举、必填、脱敏、索引 |
| API需求表 | 方法、路径、请求、响应、错误码、幂等、scope |
| 权限安全验收 | 角色、对象、动作、允许、拒绝、审计 |
| 风险待确认 | 风险等级、影响、决策人、截止时间、处理状态 |

扩展顺序：

1. 先把 12 大类和二级路线补齐。
2. 再把 S1 P0/P1 功能拆到开发规格。
3. 再扩页面、对象、API、权限、验收、测试。
4. 最后补 S2-S4 预留功能，不和 S1 工期混在一起。

## 12. 开发评审 Gate

| Gate | 时间点 | 检查内容 |
|---|---|---|
| G0 需求确认 | 开发前 | 文档编号、功能编号、验收标准存在 |
| G1 规格评审 | 开发前 | 主流程、异常、权限、数据、API 清楚 |
| G2 设计评审 | 开发前 | 架构、对象、状态、审计、索引合理 |
| G3 开发完成 | 提测前 | 自测通过，审计和错误处理完成 |
| G4 QA 验收 | 发布前 | AC 和 TC 通过 |
| G5 产品验收 | 发布前 | 页面、流程、文案、业务目标符合 |
| G6 上线复盘 | 发布后 | 反馈、故障、文档更新 |

没有 AC 的功能不能进入开发。没有 TC 的功能不能进入提测。没有审计的关键动作不能上线。

## 13. 日本式开发节奏建议

| 阶段 | 产物 | 说明 |
|---|---|---|
| 要件定義 | 产品需求、范围、角色、业务流程 | 确认做什么和不做什么 |
| 基本設計 | 页面、模块、对象、状态、权限 | 确认系统怎么组成 |
| 詳細設計 | 字段、API、异常、验收、测试 | 确认开发怎么写 |
| 製造 | 前端、后端、数据、接入开发 | 按详细设计开发 |
| 単体試験 | 单元和模块测试 | 开发自测 |
| 結合試験 | 联调测试 | 前后端、AI 工具、权限联调 |
| 総合試験 | 端到端验收 | 完整业务流程 |
| 受入試験 | 用户验收 | 产品和业务确认 |
| 運用保守 | 监控、反馈、文档维护 | 上线后维护 |

Axiqra 不一定要形式主义照搬，但这种“从要件到受入”的颗粒度很适合你现在想要的感觉。

## 14. 首轮拆解目标

| 轮次 | 目标 | 条目数量建议 | 质量要求 |
|---|---|---|---|
| Round 1 | S1 主流程和核心闭环 | 300-500 | 每条能追到文档和验收 |
| Round 2 | S1 可开发明细 | 1000-1600 | 页面、对象、API、权限、测试齐 |
| Round 3 | S2-S4 预留 | 2500-4000 | 标明阶段和依赖，不混入 S1 |
| Round 4 | 企业、生态、商业深化 | 4000+ | 和实际商业验证同步 |

数量不是目标，能开发、能验收、能维护才是目标。数量要通过结构自然长出来。
